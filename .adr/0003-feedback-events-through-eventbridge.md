# ADR-0003: Feedback events through EventBridge

- Status: Accepted
- Date: 2026-09-11
- Authority: The user asked for bounce and complaint handling with suppression, accepted that the SES suppression list is shared with another SES workload on the same account, and accepted this record on 2026-09-11. The transport was proposed here rather than chosen by the user.
- Documentation corrected: 2026-09-15. Destination types and retry boundaries are corrected below; the original no-queue consequence is superseded by the failure destination implemented in the [cleanup plan](work/clean-codebase.md) and reflected in [ADR-0008](0008-storage-capabilities-and-error-boundaries.md). The EventBridge transport decision remains in effect.
- Clerical note: 2026-09-15. The live-confirmation refusal of a second campaign (`recipient-suppressed`) became a per-recipient skip under [ADR-0011](0011-open-recipient-set-and-paced-dispatch.md): the second campaign completes with skipped rows rather than `InvalidAudience`. The EventBridge transport decision is unchanged.
- Superseded in part: [ADR-0012](0012-reputation-guardrails.md) for "neither Lambda calls any SES suppression API".

## Context

The [first slice](work/first-campaign-slice.md) could send but consumed nothing afterwards. Its configuration set was created bare, so SES emitted no events anywhere, no suppression state existed, and a hard-bounced address would have been mailed again forever. The [feedback and suppression slice](work/feedback-and-suppression.md) delivers the feedback half.

SES supports configuration-set destinations in SNS, EventBridge (the account's default bus only), CloudWatch, Amazon Data Firehose and Amazon Pinpoint. SNS and EventBridge were the relevant alternatives for this Lambda consumer in the same account and Region as the sender. [SES destinations](https://docs.aws.amazon.com/ses/latest/dg/event-publishing-add-event-destination.html).

## Decision

An event destination on the `EmailerMail` configuration set publishes `BOUNCE` and `COMPLAINT` to the **default EventBridge bus**. A second Lambda subscribes through `AWS.SES.consumeEmailEvents`, classifies each event and writes address-keyed suppression plus per-recipient history into the existing table. The same configuration set enables SES's own suppression for `BOUNCE` and `COMPLAINT`, which overrides the account-level setting for this configuration set only and touches no account-global SES setting.

EventBridge over SNS because the shapes are otherwise equivalent for one in-account consumer and EventBridge is cheaper and shorter: AWS-service events cost nothing to ingest and nothing to deliver to targets in the same account, while SNS charges per message and an SNS→SQS→Lambda path charges again per SQS request. SNS earns its keep on fan-out to several independent subscribers with per-subscription retry and DLQs; we have one subscriber. The rule is also a declaration rather than a topic plus a topic policy plus a subscription, so there is one permission boundary instead of three.

## Alternatives considered

**SNS → SQS → Lambda.** The durable option: an SQS buffer with redrive and an independent DLQ at each hop. Rejected as disproportionate for one consumer — it adds a topic, a topic policy, a queue, a queue policy, a redrive policy and a drain path, and buys durability only on the half of the problem that is already the smaller half (see Consequences).

**A reconciliation sweep over `ListSuppressedDestinations`.** Considered as the answer to lost events and rejected. It would need a new HTTP endpoint — [ADR-0001](0001-resource-owning-effect-services.md) forbids the CLI importing backend code, and the feedback Lambda has no Function URL — it would page an account-wide list shared with any other SES sender on the account, and it would pull third-party recipient addresses into our table. The self-healing echo below already provides what it would buy.

**`consumeEmailEvents`'s `configurationSets` option.** It builds the correct server-side rule pattern, but its in-Lambda re-check compares the expected string against `detail.mail.tags["ses:configuration-set"]`, which is an **array**. `matchValue` (`AWS/EventBridge/EventSource.ts:156-172`) unwraps only the expected side, so the comparison is `["x"] === "x"` → `false`, the listener returns nothing and the runtime throws `No event handler found`. The option is also typed as plain `string`, not `Input<string>`, so a generated physical name could not be passed anyway. We filter inside the handler instead, against a name pinned into the function's `env` from the exported `ConfigurationSet` declaration.

## Consequences

- **Delivery is best effort, not at-least-once.** The EventBridge reference gives SES's delivery type as "Best effort": the service attempts to send all events, "but in some rare cases an event might not be delivered". Events may also arrive out of order. An event can therefore be lost before it reaches the bus.
- **A later suppression echo can repair missing local state.** SES-side suppression is independent of whether our event arrives. For an address already on that list, a later send can be accepted without delivery and produce a bounce with subtype `OnAccountSuppressionList`, or a complaint with `complaintSubType: "OnAccountSuppressionList"`. Our classifier records those echoes. Their publication is also best effort, so the number of wasted SES calls before local recovery is not bounded to one. The classifier preserves a recovery opportunity; it cannot guarantee that the next event arrives.
- **The original no-queue choice is superseded for Lambda execution failures.** The first feedback slice relied on retries and suppression echoes without a failure queue. The [cleanup plan](work/clean-codebase.md) later added `FeedbackFailures`, configured as the Lambda asynchronous `OnFailure` destination in [Feedback.ts](../apps/backend/src/Feedback.ts), with fourteen-day retention, alarms and [synchronous replay](../apps/backend/src/ReplayFeedback.ts). Ordinary handler failures follow Lambda's asynchronous policy, normally two retries after roughly one and two minutes, before the failure destination receives the invocation record. A failed DynamoDB call can therefore remain recoverable after automatic retries stop. [Lambda asynchronous error handling](https://docs.aws.amazon.com/lambda/latest/dg/invocation-async-error-handling.html).
- **Publication and target delivery retain separate limits.** SES-side publication loss cannot reach a downstream DLQ. EventBridge retries failures to deliver to Lambda, by default for up to 24 hours and 185 retries. Beta.77's `consumeEmailEvents` does not expose target `RetryPolicy` or `DeadLetterConfig`, so this composition has no EventBridge target DLQ. An explicit EventBridge target could add one for delivery failures, but it would not capture handler failures after Lambda accepted the event; those belong to the `OnFailure` destination above. [EventBridge delivery retries](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-rule-retry-policy.html).
- **A campaign is not healed, only the address.** The echo arrives after the campaign is finalized and a non-draft campaign can never be resubmitted. A lost event therefore leaves that one campaign permanently recorded `accepted` although SES did not deliver it; what heals is the address, for future campaigns.
- **The SES suppression list is one list per account and Region**, shared with another SES workload on the same account. `suppressedReasons` on our configuration set gives us _reason_ isolation, not list isolation. Accepted as a risk because suppression is conservative: the coupled failure mode is skipping a contact we could have mailed, never mailing one we should not. The list was empty at the time of this decision. Test runs must not leave simulator addresses on it.
- **Three vocabularies name the same events** and must not be confused: the API's `matchingEventTypes` (`BOUNCE`, `COMPLAINT`), EventBridge's `detail-type` (`Email Bounced`, `Email Complaint Received`) and the payload's `detail.eventType` (`Bounce`, `Complaint`).
- **Only the default bus is supported** by the SES event destination, so no `EventBus` resource is declared; the ARN is built from `AWS.AWSEnvironment.current`. That forces the event destination to be **deploy-time-only work**: `AWSEnvironment` is in `AWS.Lambda.FunctionServices`, so reading it in a Function's outer constructor typechecks, plans and deploys — and then dies at cold start with `Service not found: AWS::Environment`. The declaration therefore lives in `Mailer.ts` as an exported `feedbackPublishing` effect that `alchemy.run.ts` yields; the Stack generator never runs at cold start, the owning module still owns the resource, and no `__ALCHEMY_RUNTIME__` guard is needed in application code.
- **The configuration-set name reaches the handler through the invocation path, not the constructor.** It is pinned into the function's `env` from the props effect, but the constructor also runs on the deploy machine, where that variable does not exist — reading it there fails planning outright. The event-source callback runs only per invocation, so the read happens there.
- Neither Lambda calls any SES suppression API, so the feedback function's role carries DynamoDB access to the table plus basic execution and **no SES actions at all**.
- **Suppression is now one of two address-keyed reasons a send is refused, not the only one.** [ADR-0004](0004-sender-owned-one-click-unsubscribe.md) added an opt-out recorded by the recipient rather than reported by a mail system, and it outranks suppression when an address carries both. Nothing in this record changed, but a reader of it should not conclude that suppression is the whole of what makes an address unmailable: `Campaigns.send` asks one `addressStatus` question answering `"mailable" | "unsubscribed" | "suppressed"`, and `isAddressSuppressed` no longer exists.

## Confirmation

`Feedback.test.ts` drives the real handler against realistic EventBridge envelopes: both echo paths suppress, `Transient` and `Undetermined` record without suppressing, `not-spam` and `auth-failure` do not suppress, a complaint with no feedback type does, a multi-recipient bounce suppresses each listed recipient, a redelivered event writes nothing new, and an event from a foreign configuration set, an undecodable payload and an unclassified event kind are all ignored without failing the invocation. The expected configuration-set name reaches the test through the same `Config` read the deployed function uses, so a hardcoded literal fails the test. Live confirmation is recorded in the [slice plan](work/feedback-and-suppression.md) under T7: both paths were driven through the deployed stack against the mailbox simulator, the feedback function recorded and suppressed each, the second campaign to each address was refused with `recipient-suppressed`, and the feedback role carried no SES action.
