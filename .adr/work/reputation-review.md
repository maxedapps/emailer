## Summary

The plan is well researched and most of its Alchemy and DynamoDB claims hold against source. Two claims do not, and both sit on the critical path of the live gate. First, the alert topic's props effect reads `AWSEnvironment.current`, and the dispatcher yields that topic transitively at every cold start; Alchemy's resource constructor evaluates a props effect whenever the resource is not already registered, the runtime Stack starts empty, and the Lambda bootstrap provides no `AWS::Environment`. The deployed dispatcher would die at init, which is the trap ADR-0003 recorded. Second, the gate expects a bounced simulator address to appear on the account suppression list; the repo's own wiki and the mass-sending evidence record that it does not. The breaker gate as sized (250 members, one evaluation point) is a race against feedback latency rather than a proof, and the plan introduces a second concurrent writer on the campaign META item without a conflict policy in the primitives. The remaining findings are documentation accuracy: the ADR misstates the IAM widening and the plan proposes in-place "clerical" rewrites of accepted ADR text that the conventions and ADR-0011's precedent reserve for lifecycle headers.

Verdict: **Changes required**. None of the corrections needs a new user decision; the topic-policy removal is the standard same-account shape and the rest is mechanical.

## Findings

### S4 — The alert topic's props effect kills the dispatcher at cold start

- **Dimension / authority:** Alchemy runtime correctness; ADR-0003:38 (accepted); ADR-0012 Decision bullet 1 and Consequences ("`AWSEnvironment.current` is read only inside the topic's props effect"); plan T3 Change and Risk/recovery, Research paragraph 3.
- **Location:** plan T3 (`alertsTopic = AWS.SNS.Topic("Alerts", Effect.gen(… yield* AWS.AWSEnvironment.current …))`), T6 (`Dispatcher.ts`: `const alarms = yield* reputationAlarms`).
- **Impact:** every dispatcher cold start dies at init with `Service not found: AWS::Environment`; no campaign dispatches on the deployed stage; every wake-up dead-letters after five receives. Found only at the T8 gate, after a full deploy cycle.
- **Evidence:** `node_modules/alchemy/src/Resource.ts:361-398` returns the existing registration only when `stack.resources[fqn]` is set; otherwise `:509` runs `yield* props.pipe(Effect.provide(Self layers))` — the props effect is evaluated in the constructor's ambient context. `node_modules/alchemy/src/Runtime/Bootstrap/Process.ts:48-63` builds the runtime `Stack` with `resources: {}`, so nothing is pre-registered at cold start. `node_modules/alchemy/src/Runtime/Bootstrap/Lambda.ts:47-57` provides `stackFromEnv`, `Credentials.fromEnv()`, `Region.fromEnv()`, `Endpoint.fromEnv()` and platform layers — no `AWSEnvironment`. The dispatcher's init yields the alarms, whose props must yield the topic for `AlarmActions: [topic.topicArn]`, so the topic's props effect runs at cold start. ADR-0003:38 recorded exactly this death for a constructor-body read; a props effect evaluated inside that constructor is the same context. The plan's T3 risk line ("resolves resources from state at cold start without evaluating props") has no source behind it. `Dispatch.ts`'s `dispatchQueue` precedent proves only that a props effect yielding another resource survives cold start, not that one requiring a deploy-only service does. No `AWS.SNS.TopicPolicy` resource exists in beta.77 (`ls node_modules/alchemy/src/AWS/SNS/`), so the policy has no deploy-only home separate from the topic props.
- **Confidence:** C3.
- **Condition:** any cold start of the deployed dispatcher.
- **Validation state:** source-proven; not run.
- **Smallest safe fix / validation:** declare the topic with plain props: `AWS.SNS.Topic("Alerts")` (optionally `attributes.DisplayName`) and drop the policy. A CloudWatch alarm publishing to a same-account SNS topic is covered by SNS's default topic policy (the `AWS:SourceOwner` statement); the `cloudwatch.amazonaws.com` + `aws:SourceArn` statement the plan copied is the cross-account / confused-deputy hardening (C2, from documentation memory — record it as deferred if the user wants it later; it would need a way to set the policy outside the runtime path). Rewrite ADR-0012 Decision bullet 1, the Consequences bullet and the plan's Research paragraph accordingly. Add to T3's verify: after deploy, invoke the dispatcher once (an empty-list campaign) before the gate, so a cold-start death is caught by the cheapest check. Keep the ADR-0003 rule in the wiki entry T9 already plans, stated precisely: a props effect is evaluated wherever the resource is first yielded, including at cold start.

### S3 — The breaker gate is a race against feedback latency, not a proof

- **Dimension / authority:** test/validation quality; ADR-0012 Confirmation ("observes the pause with reason `feedback` after at least 200 accepted"); plan T8 breaker case.
- **Location:** plan T8 (250 members, 40 `bounce+`, 210 `success+`), `IntegrationSupport.ts:67-76`, `Membership.ts:222-223`, `Identifiers.ts:3-4`.
- **Impact:** the case passes or fails depending on SES bounce-event latency and on where the random member order places the bounce contacts; a `completed` outcome makes `awaitCampaignState(…, "paused")` die on timeout minutes later; a flaky gate cannot confirm the ADR.
- **Evidence:** paced limit is 20/s (`ADR-0011` confirmation: `MaxSendRate=26`), page size 50 (`Dispatching.ts:20`), so 250 members are five slices and the breaker is evaluated at the start of slices 2–5 only. `run.accepted >= 200` is first true at slice 5 (t ≈ 12–20 s after the first send), and the trip then needs `bounced >= 10` already recorded. Member order is `MEMBER#<contactId>` with random UUIDv4 ids, so the 40 bounce sends are spread uniformly (≈32 sent before slice 5) — 10 of them must round-trip SES → EventBridge → Lambda → DynamoDB within the window or the campaign completes at slice 5 with no further evaluation. The repo records no feedback latency figure (`awaitAddressStatus` allows 60 s). Separately, `simulator("bounce", runId, n)` ignores `n`, and contacts are unique by address (`Contacts.ts:40` `EMAIL#` reservation), so 40 labelled bounce contacts cannot be imported as written. The `feedback.bounced` equals bounce rows assertion has no read path after `readCampaignFeedback` is deleted and is evaluated while events are still arriving.
- **Confidence:** C2 (timing); C3 (helper and order facts).
- **Condition:** every run; outcome depends on latency L. With L ≤ ~10 s it usually passes; with L ≥ ~20 s it always fails.
- **Validation state:** computed from repo constants; not run.
- **Smallest safe fix / validation:** (1) extend `simulator` so bounce (and complaint) addresses carry `n`. (2) Size the campaign so the trip condition is met over a long window rather than at one instant: with bounce fraction f spread uniformly, the breaker trips at the first slice k ≥ 5 where recorded bounces ≥ 0.05 × 50(k−1); at f = 0.2 that is one quarter of the bounces sent so far, so with 1,000 members (200 `bounce+`, 800 `success+`, ≈ 50 s of sending) the trip happens once L is below roughly three quarters of elapsed time — robust for L up to ~35–40 s, and the campaign cannot complete first. State the assumption in the plan and record the observed latency in Evidence. (3) Make `awaitCampaignState` fail fast on `completed` for this case (or poll for either state and assert on the result). (4) Replace "equals the count of bounce rows" with an eventual assertion: await `feedback.bounced` ≥ `progress.accepted / 20` and, after a settle window, `feedback.bounced` equals a test-side `FEEDBACK#bounce#` query count (there is a `sendRows`-style query precedent in `IntegrationSupport.ts:294-324`).

### S2 — The feedback consumer becomes a second transactional writer on the campaign META with no conflict policy

- **Dimension / authority:** correctness beyond the baseline; ADR-0011 (accepted) "conditional writes are single-attempt"; ADR-0012 Decision "Feedback is counted on the campaign … in one transaction".
- **Location:** plan T2 (`Update META ADD bounced :one` inside the feedback transaction), `Storage/Primitives.ts:131-143` (`updateIf`), `:341-373` (`runTransaction`), `Dispatching.ts` (`claimRecipient` ConditionCheck on META, `settleRecipient` Update on META, `checkpoint`, `pauseRun`).
- **Impact:** while a campaign is sending at 20/s, every send touches META twice (claim ConditionCheck, settle Update); each bounce event now also updates META in a transaction. Two transactions on one item at the same moment cancel one with `TransactionConflict`; a plain `UpdateItem` against an item in an in-flight transaction fails with `TransactionConflictException`. `runTransaction` treats any code other than `ConditionalCheckFailed` as failure and maps it to `unavailable`; `updateIf` catches only `ConditionalCheckFailedException`; both run under `Retry.none`. On the dispatcher side that dies the slice (30-minute SQS redelivery, claimed-but-unsettled rows — the ADR-0011 residual, now far likelier); on the feedback side the event goes through Lambda async retries into `FeedbackFailures` and trips `FeedbackFailuresVisible` during an ordinary bouncing campaign — the exact scenario the lane exists for.
- **Evidence:** `dynamodb.d.ts:352-363, 3580, 3729` (`TransactionConflictException` on `UpdateItem`, `TransactionCanceledException` on `TransactWriteItems`); `Membership.test.ts:132` already scripts a `TransactionConflict` cancellation, so the repo knows the code; `Primitives.ts:349-370` returns `Effect.fail(failure)` when `hasOtherReason`.
- **Confidence:** C2 (rate-dependent reachability; mechanism certain).
- **Condition:** concurrent META writes during a sending campaign with feedback arriving; most probable during the T8 breaker case itself.
- **Validation state:** not run.
- **Smallest safe fix / validation:** in `Primitives.ts`, treat a cancellation whose only non-`None` codes are `TransactionConflict` (and `TransactionConflictException` on `updateIf`) as "did not apply" and retry a bounded number of times with short jitter — this does not reintroduce the double-apply misread that `Retry.none` guards against, because a conflict provably applied nothing. Add a scripted-table unit case for each primitive. Record the policy in ADR-0012's Consequences.

### S2 — The TRANSIENT item created by `ADD occurrences` carries no record version

- **Dimension / authority:** storage design; repo convention `Items.ts:104-115` ("Every item carries the record version this code knows how to read; a different one is corrupt").
- **Location:** plan T2 (`Update SUPPRESSION#<mailbox>/TRANSIENT ADD occurrences :set`, `addressRecord` "returns the same three rows decoded").
- **Impact:** an `ADD` on a missing item creates it with only `pk`, `sk`, `occurrences`. If `addressStatus`/`addressRecord` decode the row with `StoredVersionAttribute` like every other item, the first transient bounce for an address makes that address undecodable: `addresses status` answers 503 and, through the dispatcher's `addressStatus`, the slice fails on that member. Realistic on real traffic (transient bounces are common); invisible to the simulator, which has no soft-bounce address, so the unit test is the only place it can be caught.
- **Evidence:** `Storage/Feedback.ts:54-67` and `Storage/Campaigns.ts:50-68` both require `v`; plan T2 specifies neither a `SET v = if_not_exists(v, :v)` clause nor a version-less decode for TRANSIENT.
- **Confidence:** C2 (depends on the implementer's decode choice; the plan's silence makes the convention the default).
- **Condition:** first transient or undetermined bounce for any address.
- **Validation state:** not run.
- **Smallest safe fix / validation:** specify the TRANSIENT update as `SET v = if_not_exists(v, :v) ADD occurrences :set` (values `:v`, `:set`) and assert the exact expression in `Storage/Feedback.test.ts`; decode the row with the shared version attribute like every other item.

### Specific checks requested

- **(a) Conflict retry design.** Correct as specified. The order must be client call → `Retry.none` → `Effect.retry(conflict-only predicate, jittered exponential, `recurs(4)`)` → `Effect.timeout(operationTimeout)` → cancellation decoding → `unavailable`. Retry inside the timeout is the right nesting: the whole sequence (four backoffs, 50 + 100 + 200 + 400 ms plus jitter, five requests) stays under the 5 s operation budget and within the dispatcher's `reservationFor` allowance (`operationTimeout × 2`), and a timed-out attempt is never retried — which is the property `Retry.none` exists for. A conflict-only cancellation cannot mask an applied write: `TransactWriteItems` is atomic and a `TransactionCanceledException` means the whole transaction was rejected; `TransactionConflictException` on a single-item write means the write was refused because the item was inside an in-flight transaction. Neither is a lost response. One implementation note: a cancellation mixing `ConditionalCheckFailed` with `TransactionConflict` falls to the existing `hasOtherReason` path and surfaces as `unavailable`; retrying it would also be safe (nothing applied) and would produce a clean outcome, but the conservative choice is acceptable and the test list should include that mixed case so the behaviour is pinned either way.
- **(b) Breaker gate sizing.** 400 members with 200 `bounce+` in random member order (`MEMBER#<contactId>`, UUIDv4 ids) gives eight slices; the breaker is evaluated at the start of slices 2–8, and `accepted ≥ 200` first holds at slice 5 (≈12–20 s after the first send). By then about 100 bounce sends have gone out (hypergeometric, realistically ≥80) and the trip needs 10 recorded — one in ten. Slices 6, 7 and 8 re-evaluate at about +3 s each, needing 13 of ~125, 15 of ~150 and 18 of ~175 recorded. The campaign completes after slice 8 at roughly 25–30 s. With simulator bounce latency of seconds the pause is observed before completion at slice 5 or 6; the case is deterministic for latency below about 20 s for the earliest-sent bounces, and fail-fast on `completed` turns a longer latency into an immediate, diagnosable failure rather than a hung wait. Residual: if the gate shows latency above ~20 s, grow the campaign (each extra 50 members adds one evaluation and ~3 s); record the observed latency in Evidence. The eventual-equality assertion is sound because simulator bounces produce no echoes (addresses are distinct and never listed) and no member is mailed after the pause.
- **(c) Seeded account-list entry.** Sound. `PutSuppressedDestination`/`DeleteSuppressedDestination` from the test's own credentials follow the `accountSendQuota` precedent and need `ses:PutSuppressedDestination`/`ses:DeleteSuppressedDestination` on the CLI profile, which the operator profile holds. The seed is a labelled `success+…-seed` address nothing else mails, so it cannot interfere with other cases, and the `finally` keeps the shared list as it was. Two small robustness notes, not findings: read the entry back with a short poll rather than immediately after the put in case the list read lags the write; and the sub-case that inspects a bounced address from the breaker case depends on that case having run first, so keep both in one file in that order.
- **(d) Cold-start path through `Reputation.ts`.** Safe, and the same class as F1 was checked against source. At cold start the dispatcher's constructor yields `reputationAlarms`; the runtime Stack starts with `resources: {}` (`Runtime/Bootstrap/Process.ts:48-63`), so each alarm constructor runs (`Resource.ts:361-398`) and its props effect is evaluated (`:509`). Inside it, `yield* alertsTopic` and `yield* configurationSet` are themselves resource constructors: their only hard requirement is `Stack` (provided by `stackFromEnv`); `CurrentNamespace` is `Effect.serviceOption(Namespace)` (`Namespace.ts:42`), and `ProviderModePolicy`, `RemovalPolicy`, `AdoptPolicy`, `RenamePolicy` are references or `serviceOption` reads with defaults. The topic has no props, and `configurationSet`'s props are a plain object. The outputs the alarms reference (`topic.topicArn`, `configurationSet.configurationSetName`) are `Output` proxies stored in props and never resolved at runtime, because no provider runs there; the one runtime resolution is `DescribeAlarmsHttp`'s `alarm.alarmName.asEffect()`, which reads the bound value, exactly as `SendMessageHttp` resolves `queue.queueUrl` today. Precedents already live in the dispatcher: `dispatchQueue`'s props effect yields `dispatchFailures` (`Dispatch.ts:34-49`) and `Dispatcher.ts:61` yields it at runtime; `MailerLive` yields `configurationSet` at runtime (`Mailer.ts:176`). Nothing in `Reputation.ts` reads `AWSEnvironment`, `Config`, or any other deploy-only service.
