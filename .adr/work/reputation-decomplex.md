# Decomplex review: Reputation guardrails

## Overall status

Five potential findings, none touching the four design points the user chose on 2026-09-15. The plan's core machinery — the alarm-gated dispatcher over a bound `DescribeAlarms`, the stack-owned topic per stage, the per-run breaker with its baselines, the derived transient window, feedback counters written by the consumer in one transaction — is proportionate to the problem and is either a user decision or the smallest design that makes that decision work. What does not earn its place: delivery-delay counting is a storage-and-contract feature for a signal the ADR itself says is "not acted on" and whose one useful field the counter discards (DEX-001, a user question because the Outcome names it); a fifth storage capability for a consumer that already holds both bindings it needs (DEX-002); a topic access policy whose necessity in the same account is asserted, not shown, and which drags a cold-start trap and two documentation entries with it (DEX-003, validate in the gate the plan already runs); a second 503 error shape for the semantics `StorageUnavailable` already carries (DEX-004); and a branch for an event this sender cannot produce (DEX-005).

## Potential findings

### DEX-001 — Delivery-delay counting stores rows and a counter for a signal nobody acts on, and discards the one field that would make it useful

- **Evidence:** Confirmed
- **Recommendation:** Ask user
- **Surface and location / authority:** Plan Outcome ("`DELIVERY_DELAY` publishing; campaign counters … `delayed`"), T1 (`CampaignFeedback.delayed`), T2 (`recordDelay`, `DELAY#<messageId>#<mailbox>` rows, `ADD delayed`), T3 (`DELIVERY_DELAY` on the event destination), T5 (third union member, `delay` classification, `recordDelay` per recipient), T8/T9 docs. ADR-0012 Decision: "Delivery delays are published and counted, not acted on." Not one of the four user design points.
- **Current-need evidence:** The ADR states there is no action. T9's README plan gives pause reasons and alarm meanings an operator response but says nothing about what a `delayed` count calls for. The plan puts "per-delay-type counters" out of scope, so the counter lumps `MailboxFull` and greylisting together with `SpamDetected` and `IPFailure` — and the latter two are the only delay types that are a reputation signal. `wiki/aws/deliverability.md:38` asks that soft bounces and delays be _classified_; `wiki/aws/sns-and-feedback.md:81` says only "do not independently resend". A typeless total answers neither.
- **Added burden:** A third `Schema.Union` member and decoder in `Feedback.ts`; a fifth classification; a third transactional storage operation with its own outcome decoding and a new row family (`DELAY#`) whose only reader is the dedupe condition; a `delayed` counter on META initialised at creation and projected into three submission members; a field in the shared API contract (sticky once published, modelled by the CLI and the in-memory fakes); the event-destination and `kinds` change; at least three unit cases and a README/wiki paragraph. The plan's own research admits the identity is a guess ("AWS does not state whether one event is emitted per retry").
- **Reachable practical impact:** Every delayed recipient costs one `TransactWriteItems` (two items) in the feedback consumer; a receiver greylisting a whole page produces fifty transactions for a number that changes no decision. Operators read `delayed: 37` in `campaigns get` and have no rule for it.
- **Smallest simpler alternative:** Two candidates, in order of size. (a) **Log only:** keep `DELIVERY_DELAY` on the destination, the `delivery-delay` kind and the union member, and have `record` emit one structured log line per event with `delayType`, `delayedRecipients.length`, `campaignId` and `messageId`; delete `recordDelay`, the `DELAY#` rows, the `delayed` counter, the API field and `TransactWriteItems` use for delays. The type survives, Logs Insights answers "did anything get deferred for spam-like reasons during campaign X", and nothing is stored. (b) **Drop:** leave the destination at `BOUNCE, COMPLAINT`; revisit when a delay pattern is observed.
- **Exception / boundary check:** No trust boundary, invariant or external contract depends on the count. The feedback consumer's transaction binding is still needed for the bounce and complaint counters, so the IAM widening in ADR-0012 stands either way. "Delivery delays are visible" is in the Outcome, which is why this is a question rather than an action.
- **Required behavior and simplification risk:** (a) keeps delays visible, in logs rather than in `campaigns get`; (b) drops that Outcome sentence. Neither touches the alarm gate, the breaker, the window or the address commands.
- **Bounded next step or user question:** "The plan counts delivery delays per campaign (rows, a counter, an API field) but defines no action on the number and drops the delay type. Keep as planned, reduce to a structured log line that keeps `delayType`, or leave delays out of this lane?"
- **Acceptance signal:** If (a): `grep -rn "DELAY#\|recordDelay\|delayed" apps packages` matches only the log line and its test; `CampaignFeedback` has two fields. If (b): `matchingEventTypes` unchanged and no `DeliveryDelay` member. If kept: no change; the user has decided.

### DEX-002 — A fifth storage capability for a consumer that already holds both bindings it needs

- **Evidence:** Confirmed
- **Recommendation:** Act
- **Surface and location / authority:** Plan T2 ("New capability `SuppressionStore` … `SuppressionStoreLive` binds `BatchGetItem` and `TransactWriteItems`"), T7 (API provides `SuppressionStoreLive`; `Addresses.ts` depends on `SuppressionStore`), ADR-0012 Consequences ("the API role gains … a `SuppressionStore` capability"), T9 (a new ADR-0008 table row). Not a user design point.
- **Current-need evidence:** The only consumer is the API function (T7). `Api.ts:196` already provides `AudienceStoreLive`, which binds `GetItem, BatchGetItem, PutItem, UpdateItem, Query, TransactWriteItems` on the same table (`Storage/Audience.ts:44-51`). `addressReads` — the mailability question about an address — already composes into `audienceOperations` (`Audience.ts:29`), and its module comment (`:15`) names "the mailability question the send path asks about an address" as part of the audience. The two new operations read three address rows in one batch and delete two of them in one transaction: exactly the two primitives `allPrimitives` already hands `audienceOperations`. The fifth capability therefore adds **zero** IAM actions to the API role and narrows no other role.
- **Added burden:** A new `Context.Service`, a Live layer with two bindings and two Http layers, a `Layer.provide` in the API constructor, a stub in `Api.test.ts`'s fake (and anywhere else the API's services are faked), a row in ADR-0008's capability table with a clerical correction, and a second place a reader must look to learn what the API knows about an address.
- **Reachable practical impact:** Maintenance only: two services own address rows, with `addressStatus` in one and `addressRecord` in the other, both decoding the same three keys.
- **Smallest simpler alternative:** Put `addressRecord` beside `addressStatus` in `addressReads`, add a small `addressWrites`/`unsuppress` family in `Storage/Addresses.ts` taking `TransactionPrimitives`, and spread it into `audienceOperations`. `Addresses.ts` (domain) yields `AudienceStore`. No new service, layer, stub or ADR-0008 row; ADR-0012's consequence loses the capability clause.
- **Exception / boundary check:** ADR-0008 rejected "one service per entity or method" as composition overhead and justified the four capabilities by _permission_ differences between consumers. Here there is no permission difference. The dispatcher keeps using `AudienceStore.addressStatus` as today.
- **Required behavior and simplification risk:** None affected; the operations and their transactions are identical. Risk: `AudienceStore` grows by two operations.
- **Bounded next step or user question:** Amend T2, T7, T9 and the ADR consequence before implementation.
- **Acceptance signal:** `grep -rn SuppressionStore apps packages .adr/0008*` is empty; `Storage/Addresses.test.ts` exercises `addressRecord` and `unsuppress` through `audienceOperations` or the primitives directly; `Api.ts` still provides exactly `AudienceStoreLive`, `CampaignStoreLive` and the SES/SQS Http layers.

### DEX-003 — The topic access policy is asserted as required, and brings a cold-start trap and two documentation entries with it

- **Evidence:** Supported
- **Recommendation:** Validate
- **Surface and location / authority:** Plan T3 (`alertsTopic` declared through a props effect that reads `AWS.AWSEnvironment.current` to build a `cloudwatch.amazonaws.com` publish statement with `aws:SourceAccount`/`aws:SourceArn` conditions and `Resource: "*"`), Research ("Same-account alarm publishing needs an explicit statement"), ADR-0012 Decision and two Consequences bullets, T9 (a `version-specific-traps.md` entry on `AWSEnvironment.current`). The user chose a stack-owned topic; the policy is the plan's addition.
- **Current-need evidence:** The plan cites the CloudWatch notifications page for the statement but gives no evidence that a same-account, unencrypted standard topic refuses alarm publishes under SNS's default policy. The everyday pattern — an alarm action naming a topic created with no custom policy — is how console-created and most IaC-created alarms notify, and the source-account/source-ARN conditions on that page are the confused-deputy hardening AWS recommends, not the enabling grant. I could not re-read the page in this review (no network), so this stays a validation, not an assertion.
- **Added burden:** A JSON policy with a `Resource: "*"` caveat that needs explaining; the topic becomes a props effect instead of a plain declaration; an `AWSEnvironment.current` read whose placement is a cold-start hazard the ADR must warn about ("a read in a constructor body would die at cold start") because the dispatcher yields the alarms, which yield the topic; a wiki trap entry; a risk line in T3.
- **Reachable practical impact:** If the statement is unnecessary, every later change to the module carries the cold-start trap for nothing, and the dispatcher's constructor transitively depends on a props effect it has no reason to touch.
- **Smallest simpler alternative:** `export const alertsTopic = AWS.SNS.Topic("Alerts")` with no props. If a policy is later shown to be required, add it then with the evidence.
- **Exception / boundary check:** A topic policy is a trust boundary when a foreign principal must publish; here the publisher is CloudWatch in the same account, which the default policy's owner condition is designed to admit. Confused-deputy hardening on a topic whose only subscriber is one operator mailbox is a defensible extra, not a need — if the user wants it, that is a decision, and the plan should say so instead of "needs".
- **Required behavior and simplification risk:** "Every alarm reaches a person" is exactly what the check below proves either way.
- **Bounded next step or user question:** Build T3 with the bare topic. T8 already forces one alarm to `ALARM` and reads the notification mail from the operator mailbox; if the `ALARM:` mail arrives, delete the policy, the props effect, the `AWSEnvironment.current` consequence bullet and the wiki trap line. If it does not arrive, add the statement — with the observed failure as the evidence.
- **Acceptance signal:** `Reputation.ts` declares the topic without a props effect and imports nothing from `AWSEnvironment`; the T8 `ALARM` mail is recorded in Evidence. Or: the statement stays, with the failed attempt recorded next to it.

### DEX-004 — `SuppressionListUnavailable` is a second name for the 503 the contract already has

- **Evidence:** Confirmed
- **Recommendation:** Act
- **Surface and location / authority:** Plan T1 (new error `SuppressionListUnavailable`, HTTP 503, `{ operation }`, on both `addresses` endpoints), T7 (`Addresses.ts` maps non-NotFound SES failures to it; `Api.test.ts` case). Not a user design point.
- **Current-need evidence:** `StorageUnavailable { operationId }` is already a 503 meaning "a dependency did not answer, retry" (`Schemas.ts:363-367`). The project already routes a **non-DynamoDB** dependency through it: a failed SQS enqueue is `Effect.mapError(unavailable("dispatch"))` in `Api.ts:184` and `Dispatcher.ts:77`, and ADR-0011 records the rule ("reported as a storage failure so the caller retries"). `publicly` (`Diagnostics.ts:46-61`) then logs the cause and emits `StorageUnavailable` once for every entry point. The new error carries the same status, an equivalent field and the same caller instruction.
- **Added burden:** One tagged error class in the shared contract (sticky once published), two endpoint error lists, a bespoke mapping in `Addresses.ts` that bypasses `publicly`'s logging, a CLI/fake branch, an `Api.test.ts` case and a Schemas test case.
- **Reachable practical impact:** Consumers must model two 503 tags with one meaning; the SES cause is not recorded through the boundary that records every other dependency failure unless the mapping duplicates that too.
- **Smallest simpler alternative:** In `Addresses.ts`, `Effect.mapError(unavailable("getSuppressedDestination"))` / `unavailable("deleteSuppressedDestination")` on any SES failure other than `NotFoundException`, and let `publicly` do the rest. Endpoint errors: `BadRequestNoContent, StorageUnavailable`. No new class.
- **Exception / boundary check:** No client needs to distinguish the two: the plan gives the CLI no distinct handling for it. The operation id names the SES call, so the log line still says which dependency failed.
- **Required behavior and simplification risk:** None affected.
- **Bounded next step or user question:** Amend T1 and T7.
- **Acceptance signal:** `grep -rn SuppressionListUnavailable packages apps` is empty; `Api.test.ts` asserts a 503 `StorageUnavailable` with `operationId: "getSuppressedDestination"` on a non-NotFound SES failure.

### DEX-005 — Recording transient occurrences for events without a campaign tag guards an input this sender cannot produce

- **Evidence:** Confirmed
- **Recommendation:** Act
- **Surface and location / authority:** Plan T2 ("Events without a campaign tag skip the FEEDBACK# and META items and, for transient bounces, run the TRANSIENT update as a one-item transaction"), T5 ("Events without a campaign tag keep today's behaviour (suppress, warn) and additionally record transient occurrences") and its test case.
- **Current-need evidence:** `handleEvent` (`Feedback.ts:172`) already drops every event not tagged with our configuration set. The only writer to that set is `Mailer.ts`, which tags every send with `campaignId` (`:140-141`); the API no longer sends (ADR-0011). An untagged event on our set is therefore not reachable from this system.
- **Added burden:** A second transaction shape in `recordBounce` (one item, no META), a branch in `record`, one unit case, and a sentence in the plan and README that has to explain when it applies.
- **Reachable practical impact:** None in production; the cost is the branch and its test living forever for a manual send nobody makes.
- **Smallest simpler alternative:** Untagged events keep today's exact behaviour: suppress when permanent, warn, return. Delete the one-item-transaction clause from T2 and the "additionally record transient occurrences" clause and case from T5.
- **Exception / boundary check:** The window is a campaign-send protection; an address that bounces on a hand-sent message through our set was never a campaign recipient.
- **Required behavior and simplification risk:** None affected.
- **Bounded next step or user question:** Amend T2 and T5.
- **Acceptance signal:** `recordBounce` has one transaction shape per bounce class; `Feedback.test.ts`'s untagged case asserts suppression and the warning only.

## Confirmed proportionate areas

- **Per-run baselines (`runAccepted`, `runBounced`, `runComplained`).** Counters never decrease, so a lifetime ratio that tripped stays above threshold after the operator cleans the list: a `feedback`-paused campaign would re-trip on its first slice after resume and be unresumable. Three `SET` copies in the existing conditional `enqueue`/`resume` update are the minimum that gives a run its own denominator. Kept; the accuracy of the delta when run-1 bounces arrive after resume is routed to the reviewer.
- **Counters written by the feedback consumer in one transaction.** The prior lane's report preferred a read-time query when the only reader was `campaigns get`; the breaker now needs the numbers at every slice start, and ADR-0012 alternative 4 records why a query per slice is the wrong size. The widening of `FeedbackStore` to `TransactWriteItems` is recorded in the ADR. Kept.
- **`DELAY#`-free but `FEEDBACK#`-conditioned counters.** The bounce and complaint counters ride on the history row's absence condition, which already exists; no new idempotency key is invented for them.
- **Four alarms.** The account pair partly overlaps `EnforcementStatus` in the same guard, but it fires at AWS's review threshold before AWS acts and notifies a person; the set pair isolates our own list from a co-tenant SES sender's volume, which would dilute a 2 percent bounce run to invisibility at account level. Two questions, two pairs, each a declaration. Kept.
- **The `bouncing` derived status with a string set.** The user chose three in thirty days; the derived window is the answer to the prior lane's DEX-001 (no written suppression, no un-suppress path, self-healing). `ADD` on a string set is the one replay-safe write without a condition. One batch read of three keys replaces two sequential `GetItem`s. Kept.
- **`Undetermined` counts as transient.** A two-way `Permanent ? … : transient` branch is the simplest classification; a three-way branch that stores `Undetermined` as row-only would cost more, not less. Whether that is the right policy is a reviewer question, not complexity.
- **`ignored-complaint` as a classification value.** Five literals against a kind plus a `suppress` boolean is a wash in code and clearer in tests; intention-revealing domain language. Kept.
- **The `addresses` API surface and CLI.** "See" and "clear" are the Outcome; one read and one write endpoint is the floor, the query-string form follows ADR-0004's path-parameter cap, `AddressRecord` is the three rows plus the account entry with nothing invented. `DeleteSuppressedDestination` is required because the account list blocks sends regardless of local state. Kept.
- **`SendBudget` → `SendGuard`, `DispatchBudget` → `DispatchGuard`.** The function gains alarm state and enforcement status; the old name would lie. One `GetAccount` and one `DescribeAlarms` per slice is the direct use of the user's decision. Kept.
- **`reputationThresholds`, `breaker`, `transientWindow` as exported constants** rather than configuration. Kept.
- **`Reputation.ts` as a leaf yielded by both the stack and the dispatcher.** Forced by `DescribeAlarms` taking alarm resources; the alternative (a halt flag written by a guardian) is ADR-0012 alternative 3. Kept.
- **`campaignKey` moving to `Items.ts`.** Trivial and avoids a cycle once `Storage/Feedback.ts` needs the META key. Kept.
- **`EMAILER_ALERT_EMAIL` optional at Stack level; `EMAILER_TEST_SET_BOUNCE_ALARM`.** One config read each with existing precedents. Kept.

### New candidate — bounded conflict retry in the storage primitives

- **Evidence:** Supported
- **Recommendation:** No action (keep as planned)
- **Surface and location / authority:** Plan T2 (`runTransaction` retries a cancellation whose reasons are all `TransactionConflict` or `None`; `updateIf` and `updateRecord` retry `TransactionConflictException`; `Schedule.exponential("50 millis")` jittered, `Schedule.recurs(4)`, inside `operationTimeout`), `Primitives.test.ts` cases; ADR-0012 Decision "Transaction conflicts are retried, lost responses are not" and alternative 5. Added on the independent reviewer's F4.
- **Current-need evidence:** The overlap is structural, not hypothetical. Every settle is a transaction whose second item is `ADD <counter>` on META (`Storage/Campaigns.ts:449-456`), at up to `floor(MaxSendRate × 0.8)` per second; the feedback consumer's new `ADD bounced|complained` on the same META item arrives while the run is still sending (the T8 breaker case is built on exactly that overlap: 200 bounce recipients feeding back during a 400-member run). DynamoDB rejects the loser of two concurrent transactions on one item with `TransactionConflict`, and a single-item write during a transaction with `TransactionConflictException`. Today both map to `unavailable` (`Primitives.ts:341-373`, `:131-143`), which for the dispatcher means the invocation dies, SQS redelivers after the 30-minute visibility timeout, and the page's claimed rows stay `unconfirmed` (ADR-0011's accepted residual, now triggered by a benign, frequent event); for the feedback consumer it means Lambda's async retries and then the failure queue. Shared mutable state, realistic overlap, meaningful harm: the concurrency exception in the gate is met.
- **Added burden:** One `Effect.retry` with a predicate and a schedule in each of three primitives (the predicate for `runTransaction` inspects the cancellation reasons the primitive already decodes), two named constants, four unit cases with `TestClock`, a wiki paragraph. No new item, capability, IAM, read path or contract.
- **Smallest simpler alternative considered:** (a) **Counters on a separate item** (ADR alternative 5): removes the settle-versus-feedback collision but not the API-versus-dispatcher one that already exists; the baselines could no longer be copied in the same conditional write as the `enqueue`/`resume` state change (a two-item transaction or a non-atomic read-then-write), and `beginRun`, `getCampaign` and the breaker would read two items per slice and per `get`. More surface, same class of conflict left unhandled. (b) **No retry**: the 30-minute stall and unconfirmed rows on every collision is not acceptable once the counters exist. (c) **Non-transactional feedback counter** (conditional Put, then plain `UpdateItem ADD`): still conflicts with the settle transaction, so the retry is needed regardless. The retry is the smallest correct design.
- **Exception / boundary check:** The invariant that made the project opt out of client retries — never resend a request that may have applied — is preserved: a conflict cancellation or conflict exception is reported only for a request DynamoDB rejected whole, and `Retry.none` stays on the client call. The retry is scoped to those two outcomes; condition failures, timeouts and transport errors keep their single attempt.
- **Required behavior and simplification risk:** None affected; the retry is invisible except as latency (worst case about 1.5 s over five attempts, inside the 5 s `operationTimeout`).
- **Bounded next step:** None for complexity.
