# Contact management: contacts and lists as fully managed entities

> **Status:** Complete — every task verified, ADR-0005 accepted, opened as a pull request against `main` — independent adversarial review and complexity triage both closed before implementation; see [review](contact-list-review.md) and [decomplex](contact-list-decomplex.md)
> **ADRs:** [ADR-0005: Contact identity and membership access paths](../0005-contact-identity-and-membership-access-paths.md) (Accepted 2026-09-12); constrained by [ADR-0001](../0001-resource-owning-effect-services.md)
> **Updated:** 2026-09-12
> **Note on references:** every `Storage.ts:NNN` below predates T1's split of that file and is kept as written, since this is the record of a finished slice. The modules it became are `Storage/{Items,Table,Contacts,Lists,Membership,Campaigns,Feedback}.ts`.

## Outcome and boundaries

- **Problem and target:** contacts exist only as create-and-get-by-UUID. There is no way to enumerate a list's members, find a contact by address, change one, remove one, delete one, or populate a list with more than one person at a time. `readAudience` caps at `audienceProbeLimit = 2` because it is a probe, not an audience read. Nothing prevents two contacts sharing one email address, which is incoherent with a system whose suppression and consent are keyed by address. This slice makes contacts and lists fully managed entities: unique by address, enumerable, updatable, removable, and populatable in bulk.
- **In scope:** contact email uniqueness and lookup by address; contact update including address change; contact delete; list rename and delete; paginated list-all for contacts and lists; paginated list members; member removal; bounded custom attributes on contacts; bulk import of contacts into a list; the storage access paths those need; matching CLI commands; an ephemeral `--stage test` deployment that proves the new index and the cascades against real DynamoDB.
- **Out of scope, named:** `apps/backend/src/Campaigns.ts`, `apps/backend/src/Mailer.ts`, `alchemy.run.ts`, the send guard, `Storage.readAudience`, `audienceProbeLimit`, `EMAILER_ALLOWED_RECIPIENTS`. Anything exposing mailability or consent state on a contact — no `status` field on `GET /contacts/:id`; `isAddressSuppressed` and any future `addressStatus()` belong to the parallel consent/unsubscribe slice. Also out: segmentation, CSV parsing, asynchronous import jobs, search and filtering, contact engagement history, and un-suppressing or resubscribing.
- **Approach:** no new Lambda, no new table, no new infrastructure beyond one sparse global secondary index on the existing table. Membership is written in **both directions in one transaction**, because the sparse index deliberately does not cover member items — the reverse item _is_ the contact→lists access path, and it is strongly consistent. Deletes are **paged, with `META` deleted last**, which makes a repeated `DELETE` resume. Bulk import reports **converged state, not a delta**, so re-running it is safe without an idempotency-record subsystem. `Storage.ts` is **split by item ownership first** (T1), into seven modules plus a shared test seam, as a pure refactor of already-tested code, so every new operation lands in the module that owns its items rather than in a growing monolith.

## Research

### R1 — Contract surface (Effect `4.0.0-rc.112`, verified against installed source and live execution)

- `HttpApiEndpoint.delete` exists; **`del` is module-local and not exported** (`HttpApiEndpoint.ts:1423-1432`).
- Query parameters use the **`query`** option key, not `urlParams` (`HttpApiEndpoint.ts:995`), and values are auto-coerced through `Schema.toCodecStringTree` (defined `:1081`, applied to `query` `:1087`), so `Schema.Int` is declared directly. On the **client** the `query` key is mandatory once an endpoint declares any query, even when every field is optional — CLI call sites pass `query: {}`.
- `Schema.isBetween` takes an options object: `isBetween({ minimum, maximum })` (`Schema.ts:7886-7891`).
- No pagination primitive exists in `effect/unstable/httpapi`. `Schema.optional` on a response field encodes to an **absent key**, so `nextCursor` is clean on the wire.
- **`Schema.Record` key checks silently drop entries rather than rejecting them.** `Schema.Record(Schema.String.check(Schema.isMaxLength(3)), Schema.String)` decodes `{abcd:"v", ab:"w"}` to `{ab:"w"}` — verified at runtime; the doc comment (`Schema.ts:3930-3933`) says key checks "narrow which properties are selected". Bounding attribute keys that way is **silent caller-data loss**. The correct form is `Schema.isPropertyNames(keySchema)` plus `Schema.isMaxProperties(n)` on the Record (`Schema.ts:9486-9517`, `:9358`).
- `Schema.optionalKey(Schema.NullOr(...))` distinguishes absent from explicit null. Plain `Schema.optional` also admits `{name: undefined}` — a third state with no meaning that the typed CLI client can genuinely construct.
- `Flag.keyValuePair` merges repeated `--attr k=v` into one record but **requires at least one pair** (`Flag.ts:405-406`), so it needs `Flag.optional`. `Flag.fileSchema(name, schema, { format: "json" })` reads and schema-validates a file (`:389-393`).

### R2 — Index consistency

`ConsistentRead` is invalid on a GSI. The installed SDK states it verbatim (`dynamodb.ts:7328-7333`) and the types do **not** prevent it — `IndexName` and `ConsistentRead` coexist in `QueryInput`, and Alchemy passes the request through unchanged (`Query.ts:6`). The failure is a runtime `ValidationException`. `wiki/aws/dynamodb.md:67` records the governing rule: _"A stale index result must not establish lock ownership or authorize an irreversible state transition."_ This is why the index is confined to listing (D4) and why membership reverse lookup is a base-table item (D2).

### R3 — Batch binding asymmetry

`BatchGetItem` does not follow the `Omit<…Input,"TableName">` shape of the other bindings. It takes `RequestItems` keyed by **`table.LogicalId`**, which the binding rewrites to the physical name (`BatchGetItemHttp.ts:59-70`); AWS then echoes responses keyed by the **physical** name, with no reverse mapping. `UnprocessedKeys` therefore cannot be fed back verbatim — `getTableName` will `Effect.die` on an unbound key (`:27-37`).

Handling, confined to `Storage.ts`: read with `Object.values(res.Responses ?? {}).flat()`; retry with `{ [tableLogicalId]: Object.values(res.UnprocessedKeys ?? {})[0] }`, treating an absent entry as done, in **one bounded retry pass** — not a backoff policy.

`BatchGetItem` caps at 100 keys, returns results in **no particular order**, and **silently omits missing keys** — match by key, never by index. `ConsistentRead` lives **inside** the per-table `KeysAndAttributes` value, not at the top level (`dynamodb.ts:1010-1016`).

### R4 — Transaction arithmetic, computed for every transaction in the slice

`TransactWriteItems` allows ≤100 actions and **cannot target one item twice** (`wiki/aws/dynamodb-outbox.md:31`). `addMember` already respects the second rule correctly: the list's existence check rides on its `Update`'s own `ConditionExpression` rather than a separate `ConditionCheck` (`Storage.ts:399-407`).

| Transaction                      | Actions                                                                  | Bound                 |
| -------------------------------- | ------------------------------------------------------------------------ | --------------------- |
| `addMember`                      | contact `ConditionCheck` + list `Update` + forward `Put` + reverse `Put` | 4, fixed              |
| `removeMember`                   | forward `Delete` + reverse `Delete` + list `Update`                      | 3, fixed              |
| Import, per **new** contact      | contact `Put` + reservation `Put` + forward `Update` + reverse `Update`  | 4                     |
| Import, per **existing** contact | contact `ConditionCheck` + forward `Update` + reverse `Update`           | 3                     |
| Import, whole batch              | `4n + 1` worst case                                                      | n = 20 → **81**       |
| Contact cascade, per membership  | forward `Delete` + reverse `Delete` + list `Update`                      | 3, fixed              |
| List cascade, non-final page     | `2 × Limit + 1`                                                          | `Limit = 40` → **81** |
| List cascade, final page         | `2 × Limit + 1` (`META` `Delete`, **no bump**)                           | `Limit = 40` → **81** |

The per-transaction caps matter: a cascade that builds one transaction per _page of arbitrary size_ exceeds 100 actions on any list with more than 49 members and then fails **identically on every retry**, leaving the entity permanently undeletable. Both cascade limits are therefore explicit constants, not defaults.

A cap of 20 rather than 24 on import leaves headroom so that a future fifth per-contact action is not a breaking contract change.

The "cannot target one item twice" rule also means an address change whose old and new values share a mailbox key would emit `Delete` + `Put` on one item and be rejected outright. T3 short-circuits it, and the same rule is why two submitted addresses sharing a mailbox key must be rejected before a batch is built (T1 handles this by schema refinement).

### R5 — Idempotency, honestly scoped

`wiki/aws/dynamodb-outbox.md:33` defines API idempotency as a persisted caller-scoped key, request fingerprint and original result, where _"the same key with a different payload must conflict; the same payload must recover the original operation."_ Bulk import does not meet that, and building it for one endpoint is disproportionate. The response is instead defined as **converged final state** — per submitted address, its contact id and whether it is now a member — which is identical on every call.

Note the honest limit: the list's `membershipVersion` **does** move on a re-run, because the bump is unconditional. That is deliberate and it is the safe direction. Making the bump conditional on the advisory pre-read would mean that if the pre-read says "already a member" but a concurrent `removeMember` landed in between, the import re-adds the membership **without** moving the version — the audience would change while the version did not, which is precisely the silent break `claimCampaign` exists to prevent.

### R6 — Email identity

`normalizeEmailAddress` lowercases only the domain (`Schemas.ts:17-25`); `suppressionAddress` lowercases the whole address (`Storage.ts:47`). A third derivation for `EMAIL#` would be the worst outcome. `wiki/effect/schema-and-config.md:83` requires the choice to be deliberate.

Every _consequential_ address decision in the system is already case-insensitive — suppression is, and the parallel slice's `UNSUBSCRIBE#` will be. So uniqueness follows suppression. D1 moves the derivation into `packages/api/src/Schemas.ts` beside `normalizeEmailAddress`, which puts all address normalization in one visible file and makes it callable from the contract package, where the import payload needs it.

### R7 — Test seam and lint constraints

- The Storage fake is a hand-written recording stub with scripted replies (`Storage.test.ts:35-65`). It models **no** DynamoDB semantics — no item store, no condition evaluation, no index, **and no action limit**. Condition failures are **positional**: `cancelled("None", "ConditionalCheckFailed", …)` maps slot index to outcome.
- **Replies are served by call order** (`Storage.test.ts:41-43`). Any change to the read or write count on an existing path silently returns the wrong scripted reply instead of failing to compile. `createContact` becoming a transaction and `getContactByEmail` being two reads both trip this.
- Each new `TableOperations` member forces four edits: `scriptedTable` (`Storage.test.ts:35-65`), `liveStorage` including its `named()` transaction-item switch (`Api.integration.test.ts:44-84`), the in-memory `Layer.succeed(Storage)` (`Api.test.ts:41-165`), and `StorageLive` plus its `*Http` merge (`Storage.ts:780-800`).
- Growing `Contact` edits **existing** tests: `Storage.test.ts:117-129` asserts `toStrictEqual` on a whole PutItem request, and the `contactItem` fixture at `:90-98` feeds `getContact`.
- `no-unsafe-dictionary-type` permits `Record<string, string>` and forbids `Record<string, unknown>`. `no-known-value-widening` fires when an object literal flows into an explicit `Record<string,string>` annotation — use the schema-derived type. `no-runtime-typeof` forbids `typeof x === "string"`, so attribute validation is schema-only. Assertions need a `SAFETY:` comment.
- Tests use no `vi.mock` and no `async/await`; failures go through `Effect.result`.

### R8 — Module structure, and what constrains the split

`no-service-constructor-imports` (`tools/oxlint/anti-slop/effect/rules/no-service-constructor-imports.ts:5-10`) bans a non-test file importing a project-local export matching `/^make[A-Z]/`. Per-entity modules therefore cannot export `makeContactOperations` for a runtime owner to import; they export plain operation groups (`contactOperations`) instead. That is not a loophole around the rule — nothing bypasses the Layer, and there is still exactly one service. Test files are exempt, so all three seams may keep importing `makeStorageOperations`.

`wiki/effect/services-and-layers.md:52` and ADR-0001:15 independently forbid the other extreme — _"avoid creating one service per function"_ — so the split yields **one** `Storage` tag, not a tag per entity.

A strictly per-entity decomposition does not survive contact with the code: `addMember` touches contact, list and member items; `claimCampaign` touches list, campaign and send items. Membership is therefore its own module rather than a concept smeared across two. The resulting ownership is by **item type**, which is what the keys already express: `Contacts` owns `CONTACT#`/`EMAIL#`, `Lists` owns `LIST#`, `Membership` owns `MEMBER#`/`LISTOF#`, `Campaigns` owns `CAMPAIGN#`/`SEND#`, `Feedback` owns `FEEDBACK#`, `Addresses` owns `SUPPRESSION#`/`UNSUBSCRIBE#` (split out once consent arrived — see [the follow-up](consent-identity-and-storage-cleanup.md), I2), and `Table` owns the plumbing and the single table declaration.

Alchemy logical IDs survive file moves and variable renames (`wiki/alchemy/lifecycle-and-providers.md:19`), so no `Alchemy.renamedFrom` is needed; adding one for a rename that did not happen is itself the hazard (`:30`). `tableLogicalId` must stay one exported constant, because it is simultaneously the Alchemy logical ID and the `Table:` field of every transaction action (`Storage.ts:394`, `:404`, `:411`).

The split is worth doing now rather than later because the file is 800 lines today and lands near 1,300 with this slice, with `Storage.test.ts` heading past 1,600 — and because doing it **first** means every subsequent task writes into the module where its code belongs, instead of piling into a monolith that is torn up afterwards.

### Decisions

- **D1 — One address derivation, in one file.** `suppressionAddress` moves to `packages/api/src/Schemas.ts` as an exported `mailboxKey` (trim, full lowercase — derivation unchanged) beside `normalizeEmailAddress`, and is used for `EMAIL#`, `SUPPRESSION#` and the parallel slice's `UNSUBSCRIBE#`. Uniqueness and consent are case-insensitive. The stored `email` preserves only **local-part** case, since `EmailAddress` already lowercases the domain at the HTTP boundary (`Schemas.ts:48-56`).
- **D2 — Membership is stored in both directions, in one transaction.** Forward `LIST#<listId>` / `MEMBER#<contactId>` as today, plus reverse `CONTACT#<contactId>` / `LISTOF#<listId>`. Because D4's index is sparse over contact and list `META` items only, **no index covers member items** — so the reverse item is not redundancy added to an existing path, it _is_ the contact→lists access path. The alternative is a second, inverted index, which would be eventually consistent (R2) and would index every send and feedback item.
- **D3 — Deletes are paged, and `META` goes last.** No tombstone and no marker state. Ordering `META` last is what makes a repeated `DELETE` resume, and `addMember`'s existing existence checks close the door the moment `META` is gone — the contact `ConditionCheck` at `Storage.ts:392-398` for a contact delete, and the list `Update`'s own `ConditionExpression` at `:399-407` for a list delete. The residual is a narrow window in which a concurrent `addMember` or import can add a membership to an entity being deleted, leaving an orphan; that requires two simultaneous admin operations on the same entity and is an **accepted consequence**, recorded in ADR-0005.
  - The **contact cascade** runs one transaction per membership (3 actions), so no page-size arithmetic applies.
  - A `ConditionalCheckFailed` in the list-bump slot means that list was concurrently deleted; the membership is then removed with a 2-action transaction carrying no bump. **This branch is a judgment call, not a necessity — implement it, but know what it buys.** In the ordinary interleaving the repeated `DELETE` already self-heals, because the list cascade removes both directions, so the retry simply no longer discovers the membership. The branch is only load-bearing for a _stacked_ case: the accepted orphan window above leaves a membership pointing at a deleted list, and a later contact delete then fails on it identically forever. Roughly five lines to make the accepted residual self-healing rather than accumulating; drop it if that trade stops looking worthwhile.
  - The **list cascade** pages the base-table member query at `Limit = 40`, removing both directions plus one bump per page. The **final page carries no bump** and deletes `LIST#…/META` instead: the bump is an `Update` on `listKey(listId)` and the deletion is a `Delete` on the same key (`Storage.ts:30`), so keeping both would target one item twice — a `ValidationException` raised at request validation, which never becomes a `TransactionCanceledException` and so bypasses `runTransaction`'s cancellation handling entirely (`Storage.ts:284`), failing every non-empty list's `DELETE` deterministically. Dropping the bump is safe because `claimCampaign`'s slot-0 `ConditionCheck` fails on an absent list whatever `:expected` holds (`Storage.ts:531-537`), yielding `membership-changed` exactly as a bump would.
  - The final contact transaction deletes `CONTACT#…/META` and `EMAIL#<mailboxKey>` together, **conditioned on the stored `email` still matching what was just read** — otherwise a concurrent address change landing between the read and the transaction would strand a reservation that blocks that address forever, with no API able to clear it. A condition failure there is a **failure, not a success**: return it, and the client's repeated `DELETE` re-reads and completes. Do not add a re-read-and-rebuild branch — resume already covers it. `DELETE` on an absent contact returns 404.
  - There is **no typed "incomplete" error and no `Clock` budget.** A list cascade clears ~49 memberships per transaction; at the 25 s budget the codebase already uses, that is roughly 12,000 members in one request, and import is capped at 20 per call. Beyond that the request simply times out and the client repeats the `DELETE`, which resumes. The `SendNotAttempted` precedent does not transfer: a send has an irreversible external effect that must not begin without time to record it; a delete has none.
- **D4 — The GSI is sparse and serves listing only.** Two attributes, `gsi1pk`/`gsi1sk`, written **only** to contact and list `META` items. `gsi1pk` is the entity kind; `gsi1sk` is `<createdAt>#<id>`, giving created-order listing. The index never covers `MEMBER#`, `LISTOF#`, `SEND#`, `FEEDBACK#`, `SUPPRESSION#` or campaign items, so no send or feedback write touches it and the parallel slice's new item type is unaffected. A plain inverted index was rejected for that reason and because it would make `listContacts` a _filtered_ query, running into the empty-page trap (`wiki/aws/dynamodb.md:69`).
- **D5 — Projection is `KEYS_ONLY`, and this is irreversible.** `isSameGsiDefinition` compares `Projection`, so a later change to `INCLUDE` would **replace the table** (`Table.ts:1400-1407`, `:1493-1496`). It is also better on merit: hydration through `BatchGetItem` with per-table `ConsistentRead: true` is strongly consistent and therefore **self-correcting** — a stale index entry hydrates to nothing and drops out of the page.
- **D6 — Cursors carry domain values, not database keys.** The cursor encodes `{ id, createdAt }` for entity listings and `contactId` for member listings; the key attributes are rebuilt from it. It is a Schema codec decoded at the HTTP boundary like any other untrusted input, never `as`-cast into `ExclusiveStartKey`. `nextCursor` is present **iff** `LastEvaluatedKey` is defined — never inferred from `items.length < limit` (`wiki/aws/dynamodb.md:69`).
- **D7 — Import reports converged state, not a delta** (R5), and `membershipVersion` moves on every call.
- **D8 — Named bounds.** Import batch ≤ 20. Attributes: ≤ 20 entries, key ≤ 64 chars non-empty, value ≤ 512 chars; no key pattern and no byte-size refinement, because 20 × (64 + 512) ≈ 12 KB is three orders of magnitude under the 400 KB item cap. Page size 1-100, default 25. Contact cascade: one transaction per membership. List cascade: `Limit = 40`. Attribute updates **replace the whole map**; they do not merge.
- **D9 — `Storage.ts` is split by item ownership before any new code is written** (R8). Six modules under `apps/backend/src/Storage/`, one `Storage` service tag, one table owner. The split is **T1**, a pure refactor of already-tested code, so every later task writes into the module where its code belongs instead of piling into a monolith that is torn up afterwards.
