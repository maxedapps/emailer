## Outcome and boundaries

PR #10 follow-up: [strict calendar validation](campaign-scheduling-input-validation.md) records the shared `Timestamp` refinement, CLI validation before normalization, regression evidence and review closure. It also corrects the historical timing wording below: Scheduler's 60-second precision does not guarantee that the dispatcher starts within the same wall-clock minute. The current behavior is documented in ADR-0015 and README; the original planning and review history remains below.

- **Problem and target:** a draft can only be sent now. An operator wants to queue a draft for a future instant and have the existing dispatcher run then. Target: `POST /campaigns/:id/schedule` with `{ sendAt }` moves a draft (or an already scheduled campaign) to a new `scheduled` state that records the instant; at that instant the existing dispatcher runs exactly as it does after `send`; `POST /campaigns/:id/cancel` returns a scheduled campaign to `draft`; `send` on a scheduled campaign sends now and withdraws the schedule. `GET /campaigns` shows `scheduled` with its `sendAt` because the listing already hydrates `META`.
- **In scope:** the two endpoints and the `scheduled` submission member; the instant stored in `META`'s existing `queuedAt`; the run token minted at schedule time; `beginRun` and `enqueueCampaign` admitting `scheduled`; a schedule per campaign created at runtime through Alchemy's `AWS.Scheduler.CreateSchedule` targeting the dispatch queue with the existing `DispatchMessage`; a stage-owned `ScheduleGroup` and a Scheduler execution role; `campaigns schedule <id> --at <instant>` and `campaigns cancel <id>`; unit, API, CLI and one live case each for a fire and a cancel; README and wiki; ADR-0015.
- **Out of scope:** recurring sends, send-time windows, per-recipient send-at, a `cancelled` terminal state, a Scheduler dead-letter queue or retry policy (see Research: a fire Scheduler could not deliver leaves the campaign `scheduled`; the recovery is `send`), a DynamoDB TTL or EventBridge bus rule as the clock, an SQS delay, changing the dispatcher loop, showing when the schedule was requested, rounding `sendAt` to a minute, confused-deputy conditions on the execution role's trust policy, segmentation (lane D), templates, MCP.
- **Approach:** the schedule is the existing `send` with a delay. `scheduleCampaign` writes `scheduled`, the instant into `queuedAt`, a fresh run token and the run baselines under `#state IN (:draft, :scheduled)`, which is the repeat-safe form because the same request applied twice writes the same values. Then the API deletes any schedule named after the campaign and creates one: `at(<sendAt to the second>)` in `UTC`, `FlexibleTimeWindow OFF`, `ActionAfterCompletion DELETE`, `ClientToken` = the run token, `Target.Input` = the encoded `DispatchMessage`. The fire is Scheduler sending that message to the dispatch queue; `beginRun` admits `scheduled` beside `queued` and `sending` under the same token check and is otherwise untouched, so the fire is the same transition a `send` takes today. Cancel writes `draft` and removes the token and `queuedAt` first, then deletes the schedule; send now writes `queued` under a fresh token first (the existing enqueue write, which already sets `queuedAt` to now), then deletes the schedule, then sends the wake-up. In every order a fire that lands after the write fails `beginRun`'s token check and is dropped, and a lost delete leaves a schedule that fires stale and removes itself. Assumptions taken as routine: cancel returns to `draft` rather than a new terminal state (the campaign is still a usable draft); a second `schedule` on a scheduled campaign replaces the time (delete then create under the new token); `sendAt` must be strictly after now, a contract rule checked in the domain and answered with a typed 409 (`send` is the verb for "now"), independent of what Scheduler does with a past `at()`.

## Research

- **The fire is a wake-up, nothing else.** Scheduler's SQS templated target publishes `Target.Input` as the message body, so the input is exactly `encodeDispatchMessage({ campaignId, runToken })` and the dispatcher needs no new message shape. Delivery is at-least-once; a duplicate fire is a duplicate wake-up, which ADR-0011 already tolerates. The only gap is `beginRun`'s condition, which today reads `runToken = :run AND #state IN (:queued, :sending)`: a fire on a `scheduled` campaign returns `stale` and `runSlice` returns without a trace. T2 admits `:scheduled` there and T7 proves the fire live.
- **The instant lives in `queuedAt`.** `sending`, `paused` and `completed` all require `queuedAt`, and `Storage/Campaigns.test.ts:387` pins that a `sending` item without one is corrupt. A fire goes `scheduled → sending` in one `beginRun` write with no enqueue in between. Writing the instant into `queuedAt` at schedule time gives the fired campaign the `queuedAt` it needs with no new attribute and no change to `beginRun`'s update expression: the wake-up is due at `sendAt`, and that is when it is queued. `submissionOf` reads `sendAt` from `queuedAt` for the `scheduled` state. Send now overwrites `queuedAt` with now through the existing enqueue expression; cancel removes it.
- **Which conditions change.** `beginRun` admits `scheduled` (condition only). `enqueueCampaign` admits `scheduled` so `send` on a scheduled campaign sends now under a fresh token (condition only; the expression already sets `queuedAt`); a fire under the old token then fails the token check. `resumeCampaign` must not admit it (`resume` on a scheduled campaign returns the campaign unchanged, as it does for `draft`). `claimRecipient`, `skipRecipient`, `checkpoint`, `completeRun` and `pauseRun` all require `sending` and are untouched. No path returns a campaign to `draft` with a `queuedAt`, so `if_not_exists(startedAt, ...)` and the existing reads stay correct.
- **Repeat-safe forms (ADR-0013).** `scheduleCampaign` under `#state IN (:draft, :scheduled)`: the write is a full overwrite of `queuedAt`, `runToken` and the baselines, so a retry after a lost response re-applies the same values, and a reschedule is the same write with new values. `unscheduleCampaign` under `#state IN (:scheduled, :draft)`: `draft` is the state this very request leaves behind, and the domain only calls it for a `scheduled` campaign. `enqueueCampaign` keeps its `(#state = :queued AND runToken = :run)` disjunct.
- **Scheduler calls are made repeat-safe by name and token.** The schedule is named after the campaign id (stable, matches the `Name` pattern), so a retry of `create` after a lost response carries the same `Name` and the same `ClientToken` (the run token) and succeeds idempotently; without the explicit token the distilled client generates a fresh one per attempt and the retry would answer `ConflictException`. `create` deletes any schedule of that name first (ignoring `ResourceNotFoundException`), which is what makes a reschedule and a repair after a lost create the same one path; a `ConflictException` can then only be a concurrent operator, is retried by the client with backoff (it is classed retryable) and then answered as `StorageUnavailable`. `remove` ignores `ResourceNotFoundException`.
- **Ordering and the cancellation race.** Table first, Scheduler second, in every operation. Schedule: after the `scheduled` write a crash before `create` leaves a campaign `scheduled` with no schedule; the operator sees it stay `scheduled` past its minute and repeats `schedule` or uses `send`. Cancel: after the `draft` write a crash before `remove` leaves a schedule that fires with a token the item no longer holds, fails `beginRun`, and deletes itself under `ActionAfterCompletion: DELETE`. Send now: the same. A schedule that Scheduler could not deliver (no retry policy or dead-letter queue is configured; Scheduler's defaults retry for up to a day) also leaves the campaign `scheduled`; recovery is `send`. So do two concurrent reschedules of one campaign that leave the table and the schedule under different tokens: the fire is stale, and `send` recovers. Recorded in README.
- **Precision.** Scheduler fires "between `1:00:00` and `1:00:59`" for a schedule at `1:00`; nothing defines the window for `1:00:45`, so a mid-minute instant may fire seconds before or after it. `at()` takes seconds, so the service renders `at(${sendAt.slice(0, 19)})` with `ScheduleExpressionTimezone: "UTC"`. The contract promises the minute of `sendAt`. The live gate uses a whole-minute instant so "not before `sendAt`" holds under either reading, and records the observed offset in ADR-0015's Confirmation.
- **The group per stage is mandatory.** A runtime-minted schedule belongs to no Alchemy resource, so `alchemy destroy` cannot see it; one left on a torn-down stage would fire at a deleted queue, with an execution role that no longer exists. Binding `CreateSchedule(role, group)` puts every schedule in the stack-owned group, whose delete is `DeleteScheduleGroup`, which AWS documents as deleting every schedule in it. Alchemy names the group deterministically per stack and stage (`PhysicalName.ts:28`); no explicit name is needed.
- **Execution role.** Alchemy mints a `scheduler.amazonaws.com` role only for its deploy-time `Schedule` resource; the runtime binding expects the application to declare an `AWS.IAM.Role` with that trust and `sqs:SendMessage` on the dispatch queue (`CreateSchedule.ts:52-77` is the canonical example). The binding grants `iam:PassRole` on it to the API function. A freshly created role can take over a minute to become assumable (`ExecutionRoleNotAssumable`); the role is created during the deploy, before the API function that depends on it, and the first `schedule` call in a live run comes minutes later. If it ever answers 503 right after a first deploy, wait a minute and repeat.
- **Where the account id is not needed.** The role's policy takes the queue ARN from the resource attribute (`queue.queueArn`), and the binding composes the schedule ARN pattern at deploy time; nothing in the runtime path reads `AWSEnvironment`, which the wiki warns is deploy-time only.
- **`Flag.date` is not the flag.** It decodes through `new Date(string)`, so `2026-09-20T09:00` is local time on the operator's machine. `Schema.DateTimeUtcFromString` reads zone-less input as UTC (verified under a non-UTC `TZ`), accepts offsets, and `DateTime.formatIso` renders the `.sssZ` form the contract's `Timestamp` requires. The wiki has no `DateTime` guidance; T6 adds the one paragraph.
- **Past `sendAt`.** A contract rule, not a Scheduler workaround: an instant at or before now is an operator mistake, and `send` exists for "now". The domain compares `Date.parse(sendAt)` with `Clock.currentTimeMillis` and fails `SendAtNotInFuture` (409, beside `EmailAlreadyUsed` and `AddressOptedOut`; not 400, so it does not share a status with the empty-body `BadRequestNoContent`). An instant a few hundred milliseconds ahead passes the check and renders as an `at()` in the current second; the API reference does not say what Scheduler does with that, so T7's manual walkthrough probes a mid-minute instant a few seconds ahead (and optionally a past `at()` directly) and records the answers. If Scheduler refuses such an instant with a `ValidationException`, the operator sees a 503 for an input nobody sends on purpose and uses `send`; that is documented, not mapped.
