## Outcome and boundaries

- **Problem and target:** a recipient has no way to stop receiving mail. Bounces and complaints suppress an address, but a person who simply does not want the mail has no mechanism at all — not in the message, not in the API. That is the last missing requirement before the recipient set can be opened beyond the configured allowlist, and it is required of bulk senders by Google and Yahoo independently of volume. This slice delivers RFC 8058 one-click unsubscribe end to end: every outgoing message carries `List-Unsubscribe` and `List-Unsubscribe-Post` plus a visible footer link, an unauthenticated endpoint honours the opt-out durably and idempotently, and an unsubscribed address is refused before any SES call.
- **In scope:** a signed, opaque unsubscribe token; a second public Lambda serving `GET`/`POST /unsubscribe/:token` as HTML; an address-keyed unsubscribe record in the existing table; a single `addressStatus` storage read replacing `isAddressSuppressed`; the two headers and a fixed footer on every send; `EMAILER_POSTAL_ADDRESS` as required configuration; unit tests plus a live ephemeral `test` verification that includes reading the delivered message's DKIM `h=` tag.
- **Out of scope:** consent evidence on the contact (`consentedAt`, source) and double opt-in — the user deferred both on 2026-09-11, with optional double opt-in named as possible later work; resubscribe and un-suppression; preference centres and topic-level subscriptions; an open contact list; bulk fan-out; scheduling; open/click tracking; HTML bodies; `mailto:` in `List-Unsubscribe`; a `Reply-To` address; SPF and DMARC records; and production rollout.
- **Approach:** one new domain module and one new Lambda, per [ADR-0001](../0001-resource-owning-effect-services.md). No new table and no GSI — the unsubscribe record is a new address-keyed item type beside suppression. The signing key is minted by `Alchemy.Random` rather than configured by hand, because no person ever needs to know it. The one structural simplification is `addressStatus`: rather than adding a second address question beside `isAddressSuppressed`, the two collapse into one operation answering `"mailable" | "unsubscribed" | "suppressed"`, so `Campaigns.send` ends this slice with the same number of guards it began with.

**Why unsubscribe is a separate concept from suppression, not a sixth suppression reason.** They are written by different parties and have different futures. Suppression is a fact reported by a mail system; unsubscribe is a decision made by a person. Resubscribing is a legitimate future operation, un-suppressing a hard bounce mostly is not, and an operator reading a refusal has to be able to tell "the mailbox rejected us" from "the human said no". They share a shape — address-keyed, monotonic, conditional-write — and nothing else.

**On the standing refactor licence.** The user asked on 2026-09-11 that work land as if the system had been built that way from the start, with large refactors welcomed. An earlier draft of this plan extracted the five audience checks out of `Campaigns.send` into an `Audience.ts` decision. That extraction was **dropped in review**, and the reasoning is recorded rather than hidden: after `addressStatus` the guard count does not grow, so there was no accumulation to undo; the check order it proposed silently reversed a precedence the previous slice pinned by name in `Campaigns.test.ts:431`; and the one invariant worth protecting — that `getList` is read before `readAudience`, because its `membershipVersion` is the fence passed to `claimCampaign` — would have stayed unprotected either way, since the extracted function receives the members rather than reading them. The licence is permission, not obligation. `addressStatus` is the refactor this slice earns.

## Research

Findings that shaped the design. Sources are the installed Alchemy `2.0.0-beta.77`, Effect `4.0.0-rc.112`, `@distilled.cloud/aws` `1.0.0-rc.9`, and current AWS / RFC / mailbox-provider documentation. Citations were independently re-verified in review.

**The headers are settable, and AWS documents this exact path.** `SendEmail` with `Simple` content accepts a `Headers` list (`sesv2.ts:995-1008`), `List-Unsubscribe` and `List-Unsubscribe-Post` are supported header names, and they are explicitly independent of `ListManagementOptions`. The disallowed custom headers are `BCC`, `CC`, `Content-Disposition`, `Content-Type`, `Date`, `From`, `Message-ID`, `MIME-Version`, `Reply-To`, `Return-Path`, `Subject`, `To` — none of which we set.

**DKIM coverage is the one unverified external fact.** RFC 8058 requires both header fields to appear in the `h=` tag of a valid DKIM signature, and AWS documents nowhere which headers SES puts there. Captured SES mail shows the signer enumerating the headers actually present rather than a fixed list, including both unsubscribe fields under a sender's own Easy DKIM `d=`; those captures are raw/SMTP sends, so coverage of the `Simple` + `Headers` path is inference. **Recorded fallback, honestly scoped:** if T9 finds `h=` without the two fields, the message must be built as `Content.Raw` MIME inside `makeSubmit`. That is not a one-line change — it means composing the MIME by hand, RFC 2047 encoded-words for non-ASCII subjects (`Mailer.test.ts:84` fixtures `"Grüße 😀"`), a transfer encoding for the body, and reshaping every assertion in `makeSubmit`'s describe. Storage, the token, the endpoint, the guard and the footer are unaffected. This is why T9 reads `h=` before anything else it does.

**Verify `h=`, never Gmail's button.** Gmail's inbox-level unsubscribe control is reputation-dependent, so a correctly signed first message from a fresh domain can show no affordance. Absence would be a false negative.

**No `mailto:` and no `Reply-To`.** RFC 8058 requires one HTTPS URI and makes `mailto:` optional. Google's and Yahoo's bulk sender requirements cover authentication, alignment, one-click unsubscribe and spam rate; neither asks a sending domain to accept mail or carry a monitored reply address. CAN-SPAM accepts a web-based opt-out in place of a reply address. `example.com` does not receive mail and will not, and the user declined a `Reply-To` on 2026-09-11; [ADR-0002](../0002-domain-sending-identity.md) records the reasoning and the residual cost.

**CAN-SPAM also wants a postal address in the body.** It applies to commercial marketing mail to US recipients and lands in the same footer as the visible unsubscribe link, so it is in scope here rather than a separate concern. It is required configuration, not optional: a missing value must fail construction the way `EMAILER_ALLOWED_RECIPIENTS` does, because the alternative is silently sending non-compliant mail.

**The cross-function reference dictates the declaration form.** `Api.ts` must embed a link pointing at the unsubscribe function's URL, so it needs a reference to that resource. The inline class form used by `Api.ts` and `Feedback.ts` is `cls.Self.pipe(provideClassLayer(cls.make(props, impl)), effectClass)` (`Platform.ts:455-461`) — it **always** builds, with no `serviceOption` guard. Yielding `UnsubscribeFunction` inside `apiProps` would therefore re-run the unsubscribe function's props _and_ init inside the API Lambda on every cold start, resolve its `Config` reads against the API's `process.env`, and pull its handler into the API's bundle. The bare-tag form (`Platform.ts:394-420`) resolves through `Effect.serviceOption`: at plan the provided `.make` Layer supplies the real instance. **The tag must therefore live in a module that does not import the handler**, and the `.make` Layer must be provided to the Stack program or planning fails with `missingImplementation` (`Plan.ts:383-388`).

**What the source does not settle**, and T7 checks early rather than at the end: the bare tag's `onNone` path registers `resource(id, undefined)` — props undefined, unlike the resource stand-ins `Feedback.ts` reads today. Whether `unsubscribe.functionUrl` is safe to reference from `apiProps` at the API's **cold start** cannot be established from `Platform.ts` alone. T7 therefore runs `alchemy plan` as soon as the wiring exists, and T9's first deploy is the runtime proof. The previous slice's two live-only defects were both of exactly this kind.

**`.ref()` is not the answer.** `upstream()` has no `RefExpr` branch (`Output.ts:789-816`), so a ref records **no dependency edge** and resolves by reading persisted state, failing if the target was never deployed. Deploy order would become manual. A direct value reference records the edge and `Apply` blocks on it (`Apply.ts:908`, `:1005`), so declaration order in the Stack generator is irrelevant.

**The URL and the secret are handler-phase reads.** Every `Config` read inside a Function's impl is intercepted: at plan it loads from the **deploy machine's** environment and binds the value into the function's env; at runtime it reads back from `process.env` (`Platform.ts:553-592`). Neither `EMAILER_UNSUBSCRIBE_URL` (an Output of another resource) nor the `Random` secret exists on the deploy machine, so reading either inside `MailerLive` — which is built at init — fails at **plan**, exactly as `EMAILER_CONFIGURATION_SET` did in the previous slice. Both are read per invocation instead. `EMAILER_POSTAL_ADDRESS` is ordinary configuration present on the deploy machine and stays with `mailerAddresses`.

**A `Redacted` in props `env` is deployed as plaintext.** The Lambda provider does not marker-pack props env; the AWS client's `SensitiveString` encoder unwraps it (`@distilled.cloud/aws/src/sensitive.ts:40-53`). The deployed variable holds the raw value, and `Config.redacted` reads it back in the handler with no unwrapping. Redaction here is a logging protection, not an at-rest one.

**Plain `HttpRouter`, not an `HttpApi` group.** `HttpApiBuilder.layer` dies if any group of the API lacks handlers (`HttpApiBuilder.ts:91-99`), so an unsubscribe group cannot be added to `EmailerApi` without breaking the API Lambda. Against that, two HTML routes need none of `HttpServer.layerServices`, errors in an `HttpApi` default to JSON encoding while `asText` demands `Encoded: string`, and there is no contract to publish because the consumers are browsers and mail providers. `HttpRouter.toHttpEffect` self-provides its router (`HttpRouter.ts:582-598`).

**Ignoring the one-click body is a property of declaring no payload.** The only 415 source is `decodePayload`, reached only when a payload is declared (`HttpApiBuilder.ts:707`); a plain router never touches the body at all. This satisfies RFC 8058's requirement to accept both the multipart and URL-encoded forms without parsing either. The confirm form uses `method="post"` with no `action`, so the browser posts to the current URL and the token is never interpolated into markup — which also sidesteps HTML escaping entirely.

**GET must not act.** Scanners, link prefetchers and security products issue GETs. The wiki records this: "A GET request to an unsubscribe link must not trigger a one-click unsubscribe merely because a scanner fetched it; use the RFC's POST mechanism."

**A page that claims success must mean it.** Mail providers treat a 2xx as the opt-out being honoured and do not retry, so rendering the confirmation without a durable write turns a transient fault into a permanent one on the single interaction the recipient gets. This needs no machinery — an uncaught `StorageFailure` already becomes a logged 500. It needs the absence of a mistake: do not catch that failure in order to return a uniform page.

**HMAC has no Effect-native form here.** `effect/Crypto` offers `digest` and randomness but no HMAC, sign/verify or key import (`Crypto.ts:76-154`), and `NodeCrypto.layer` re-exports exactly that interface. `node:crypto`'s `createHmac` is synchronous, so it needs no `Effect.promise`; Web Crypto's `subtle.sign` is Promise-based for no benefit. Hand-rolling HMAC from `digest` is rejected outright. The import needs `// oxlint-disable-next-line effecttsgo/node-builtin-import`, the convention already used at `apps/cli/src/Commands.test.ts:8`.

**There is no index to look an address up by.** At this baseline the table declares `pk`/`sk` only, there is no GSI, no `scan`, and both existing `query` call sites are `pk = … AND begins_with(sk, …)` on the base table. An address-keyed item is the only cheap lookup, which is why unsubscribe state is keyed by address rather than stored on the contact — and `createContact` has no uniqueness condition today, so two contacts may share an address and contact-keyed state would leave the second one mailable.

**Coordination with the parallel contact-management slice.** [ADR-0005](../0005-contact-identity-and-membership-access-paths.md) is being drafted in parallel and overlaps this slice in one file. It promotes `suppressionAddress` to an exported `mailboxKey` used by `EMAIL#`, `SUPPRESSION#` and this slice's `UNSUBSCRIBE#`; the derivation is unchanged, so T2 should take whichever name exists when it merges rather than introducing a second one. It also adds an email-uniqueness reservation on contacts and a sparse `KEYS_ONLY` index over `META` items only. Neither changes this slice's conclusion: address-keying still matches what a bounce payload carries and what SES itself keys on, and the new index does not serve address lookup. T2 and that slice both rewrite large parts of `Storage.ts`, so whichever lands second rebases onto the other rather than merging blind.
