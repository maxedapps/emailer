## Outcome and boundaries

Refactor Emailer into a simpler application with explicit capabilities, trustworthy persistence, immutable unsubscribe identity, useful error reporting, and recoverable feedback failures. Remove obsolete abstractions and checks rather than keeping compatibility facades.

The user explicitly permits redeploying everything owned by this application, erasing development data, and replacing all existing unsubscribe links. No migration, old-link decoder, or data-preserving rollout is required. This authorizes the reset approach for a future implementation; this planning task performs no deployments, data changes, or code changes.

Preserve the current single-recipient/allowlisted send slice, one DynamoDB table, existing API operations, transaction-based send claim, no automatic retry of uncertain SES submissions, address-based suppression/consent, GET/POST unsubscribe semantics, and the policy that an already opted-out contact cannot move to another address. Preserve ADR-0005's accepted cascade-race tradeoff. Do not introduce bulk dispatch, a generic repository framework, automatic replay workers, a replacement logging platform, or dependency upgrades.

### Execution order

Execute **T1 → T4 → T2 → T3 → T5 → T6 → T7 → T8 → T9**. T4 removes unsubscribe's contact lookup before T2 introduces its final PutItem-only capability. T2 includes backend error-boundary conversion so removing the old storage facade does not require a temporary compatibility layer. T6 subsequently changes HTTP lifetime and CLI reporting.

Implementation was requested on 2026-09-14. ADR-0007 and ADR-0008 are Accepted as of that date; ADR-0004, ADR-0005 and ADR-0006 carry in-place supersession links and keep their original rationale. Per-task status and evidence are recorded against each task below.

### Critical implementation details

- **Token:** `v1.<unpadded base64url(mailboxKey(email))>.<lowercase hex HMAC-SHA256("v1." + payload)>`. Sign version and payload together. Validate structure/length/alphabet, then signature, then canonical decoding and shared mailbox schema. Address maximum is currently 254 ASCII bytes; encoded payload 339 characters; token 407 characters. Derive the limit rather than retaining the current router cap. Encoding is not confidentiality; do not log tokens, URLs or decoded addresses. A representative Function URL plus maximum token fits SES's header limit; test the actual generated URL/header too.
- **Codecs:** use RC112 `Schema.decodeTo` and `SchemaGetter.transform`: `{ S: ... }` ↔ string, `{ N: Schema.NumberFromString }` ↔ number, `{ M: Schema.Record(Schema.String, StringAttribute) }` ↔ string map. Compose domain refinements and `Schema.optionalKey`; tolerate unrelated key/index attributes. Keep meaningful campaign state validation. Small existing write/expression helpers can remain if they are clearer; a decoder cleanup does not require rewriting every writer.
- **BatchGet:** accumulate completed responses; retry only pending keys, re-keying physical response names to Alchemy's logical table ID; preserve ConsistentRead. Start with four total attempts, jittered exponential delays starting at 100ms, and one outer five-second logical timeout. The private incomplete-batch retry signal must become StorageFailure on exhaustion. Do not multiply the timeout per retry or apply this retry policy to SES.
- **Import:** existing-contact branch retains contact existence and adds `EMAIL#mailboxKey(candidate.email)` holder equality in the same transaction. At twenty candidates the maximum is 81 actions. Do not compare case-preserving contact email text directly against import spelling. Changed/deleted/reassigned reservation fails without membership writes; preserve the exact transaction request/token relationship.
- **Time:** the ordinary one-page send path can spend roughly 30s in six database calls, then up to 18s claiming, submitting and finalizing. 60s Lambda and 70s CLI are initial settings to validate, not a hard completion guarantee: pagination, initialization and runtime overhead exist. The generated client currently only exports the timeout constant; the CLI is its only consumer and actual enforcement owner.
- **Errors:** storage keeps operation ID, unavailable/corrupt classification and original cause. Internal send failures keep campaign/send IDs and cause until HTTP translation. Log only safe classification/identifiers/cause tags; do not dump raw SDK payloads or schema input. Known storage failures crossing feedback/unsubscribe boundaries must remain failures, with safe diagnostics before any framework error formatting. Expected public errors keep their schemas and status codes. Unexpected defects remain failures/500s with diagnostics.
- **CLI:** root `Effect.tapCause` wraps command execution including NodeServices provisioning. Preserve Cause/exit behavior and stderr output. RC112's `Runtime.getErrorReported` returns false for errors the CLI has already rendered; interruption-only causes need no duplicate diagnostic. Do not merely enable NodeRuntime logging with a logger provided inside the program: the runner reports outside that context and can write to stdout. Remove CommandFailed instead of retaining another already-reported wrapper.
- **Replay:** Lambda's queued record contains requestPayload and original failure metadata. Accept the configured unqualified function ARN or that exact ARN plus `:$LATEST`; reject other qualifiers/accounts/regions/functions. Invoke the configured target with the original requestPayload, never a message-selected ARN. A new synchronous invocation's HTTP 200 with FunctionError is still failure. The original record's failure metadata is expected and must not prevent a repair attempt.
- **Destination:** OnFailure's ARN does not grant SQS permission in the pinned provider; construct native SendMessage binding in Feedback's constructor, without calling it. Do not give Feedback receive/delete permission. OnFailure covers events Lambda accepted, not upstream SES/EventBridge publication or target-delivery loss.
- **Monitoring:** queue-visible-messages and DestinationDeliveryFailures alarms are concrete console-visible signals. Do not claim notifications without a configured channel. Keep alarm creation deploy-only, using already-resolved function/queue attributes; do not resolve the inline function inside its own runtime/props.
