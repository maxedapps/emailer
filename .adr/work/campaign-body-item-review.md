## Confirmations

The eight questions the briefing named, where the plan's claim held under inspection:

- **Repeat-safety and the `unavailable` mapping (1).** `runTransaction` draws one token per logical call and the store, not the client, sets `ClientRequestToken` (`Primitives.ts:425-427`), so the client's resend of a lost response is byte-identical and DynamoDB answers success without re-applying. `isConflictCancellation` (`:56-64`) is false whenever any reason is `ConditionalCheckFailed`, so a condition failure is never retried under a new token and reaches the caller as `committed: false`; under a freshly generated identifier neither key can pre-exist, so that outcome is an anomaly and `unavailable("createCampaign")` matches `createContact`'s identifier slot (`Contacts.ts:213-217`). Conditions evaluate per full primary key, so `META` and `BODY` sharing `pk` is irrelevant, and a transaction may target two different items in one partition.
- **`Struct.fields` and assignability (2).** `readonly fields: Fields` with the exact spread example is at `Schema.ts:3495-3509` in the installed rc.112; the repo has no prior use, as the plan says. The composed `Campaign` type has the same members as today (order aside), so every existing `Schemas.Campaign` fixture and `Campaigns.create`'s literal still type; a `Campaign` is assignable wherever `CampaignSummary` is expected, which is why T1 alone leaves `pnpm typecheck` green (confirmed green at HEAD).
- **`ALL_NEW` and the dispatcher placement (3).** `beginRun` is `updateIf` with `ReturnValues: "ALL_NEW"` on `campaignKey` (`Campaigns.ts:325-337`); it returns that item's attributes and nothing else. The three pause exits (`Dispatching.ts:100-139`) precede `listMembers` (`:141`), so the read placed after `:147` is not paid on a pause. `reservationFor` is unchanged because the read precedes the first `remainingUntil` check (`:192-195`). The budgets the ADR quotes are the real ones: `Api.ts:33` (60 s) and `Dispatcher.ts:21` (5 min). Finding 1 is the one inaccuracy.
- **Test seams (4).** `scriptedTable` serves replies by per-operation call order (`Testing.ts:66-101`), so a two-`readItem` `getCampaign` consumes two `getItem` replies and the five-call case at `Campaigns.test.ts:216-294` needs ten, interleaved, as the plan says. The three `putItemRequests[0]` reads are at `:153, 195, 330` and move to `transactionRequests[0].TransactItems[0|1].Put.Item`, each in a fresh table so index 0 is right. `beginRun` expectations carrying `text: "Body"` are at `:505, 548, 584`. The reserved-word check inspects expressions only (`:56-79`); the BODY Put adds no expression beyond `attribute_not_exists(pk)`. The `beginRun` fake at `Dispatching.test.ts:164-180` is the only one that returns a run; the other two are `notExercised`.
- **Consumers of `text` on `send`/`resume`/`list` (5).** None. CLI cases assert `toMatchObject({ submission })` or compare two transition responses to each other (`Commands.test.ts:568-574, 607-614, 639-641`); the integration suite reads only `.submission.state` from `sendToSimulatorList` and `resume` results (`Api.integration.test.ts:112, 198, 231, 286, 374, 392-396`); `README.md` shows no response body; `apps/mcp/src` has no campaign reference; every `store.reads` assertion in `Api.test.ts` is `toHaveLength(0)` on a rejected request, so a new read label from `send` breaks nothing.
- **Integration `Campaign` annotations (6).** `awaitCampaignState` (`IntegrationSupport.ts:331-363`), `campaignFeedback` (`:365`) and `awaitCampaignFeedback` (`:376-385`) are typed `Schemas.Campaign` and consume `client.campaigns.get` results only; `get` keeps `Campaign`, so they still typecheck. `sendToSimulatorList` (`:239-252`) returns whatever `send` returns and its callers use `.submission.state`.
- **Sequencing (7).** T1 green, T2 red until T3: `CampaignStoreOperations` is `ReturnType<typeof campaignStoreOperations>` (`Campaigns.ts:629`), so after T2 the three object-literal fakes (`Campaigns.test.ts:89`, `Api.test.ts:354`, `Dispatching.test.ts:157`) lack two required members and `Dispatching.ts:96` destructures a removed field. The plan states this at T2 Verify. The only runtime-red case between T1 and T3 is the one in finding 4.
- **ADR-0014 numbers (8).** 130 units for a 65 KB META update inside a transaction, about 7 settlements a second against 1,000 units per partition, about 1.5 with a 256 KiB HTML body, 25 × 256 KiB above the 6 MB buffered Function URL response, 60 s and 5 min budgets, 400 KB item ceiling: each is consistent with the cited AWS pages and with `Api.ts:33`, `Dispatcher.ts:21` and `Schemas.ts:7`. Its ADR-0005 and ADR-0011 characterisations are accurate; finding 3 (alternative 3's "one write unit") and finding 7 (the ADR-0013 line) are the two inaccuracies.

## Verdict

**Clear.** Nothing found would make the implemented result wrong, infeasible, unsafe or mis-sequenced: the two-Put tokened create is repeat-safe and its anomaly mapping is right; the schema composition works in the installed Effect and the types line up so that T1 alone typechecks; `beginRun` cannot return a sibling item; the dispatcher's read sits outside every pause exit and inside the budget; the test-seam arithmetic (interleaved replies, transaction indices) is correct; nothing reads `text` from a transition or listing response; the integration helpers still typecheck; and the plan's statement of which task leaves typecheck red is correct.

Findings **1**, **2** and **3** should be applied during implementation because they are record accuracy in an ADR that will be accepted: 1 and 3 are rewordings (T5 owns the ADR text; the plan's own lines 29, 44, 45 go with them), 2 is a one-line type change in T2 plus one consequence line in T5, and the plan must say which of the two bindings decisions it takes. Findings 4 to 7 are plan-text clarifications that save the implementer a re-investigation (4), a no-op instruction (5), an unstated choice (6) and three wording fixes in ADR-0014 (7). No further planning round is needed.

**The five material changes, checked:**

- **(a) Two `recordOnce` puts, BODY first.** Repeat-safe under ADR-0013:23 as written: each put is `attribute_not_exists(pk)` with the condition failure reported as done (`Primitives.ts:126-132`), both keys are freshly generated, so a client resend of a lost response on either put lands on its own item and is answered done, and a resend of the whole `create` is a new identifier (ADR-0013:39). The orphan is genuinely unreachable: the index attributes are written by `listingAttributes` on the META item only (`Campaigns.ts:202`; `Items.ts:14-18`), `readEntityPage` hydrates by `keyOf(id)` = `campaignKey` (`Primitives.ts:360`), every store read of a campaign goes through `campaignKey`, `bodyKey` or `sendKey`, and the only base-table partition queries in the backend are on `LIST#`/`CONTACT#` prefixes (`Membership.ts:218, 329, 409`); the one `CAMPAIGN#` partition query in the repo is the integration helper's `begins_with(sk, "SEND#")` (`IntegrationSupport.ts:415-419`), which cannot match `BODY`. A crash after META with a lost response leaves a complete, listed campaign and a 503, which is ADR-0013's accepted "human retrying a create gets a new entity", not corruption. Holds.
- **(b) `getCampaignBody` without an option.** Both callers hold META first: `getCampaign` reads META and returns `none` before any body read (plan line 72); the dispatcher reaches the read only after `beginRun` returned `running`, and `beginRun`'s condition `runToken = :run AND #state IN (...)` fails on an absent item (`Campaigns.ts:325-341`), so `stale` exits at `Dispatching.ts:92-94` before the read. With BODY written first, a META that exists implies its BODY was written, and no delete exists, so an absent body is corrupt for both. Holds. The test that pins the absent-body case is "META without BODY is `corrupt`" through `getCampaign` (plan line 78), which exercises the same decode path the dispatcher uses.
- **(c) `send`/`resume` unchanged, no `getCampaignSummary`.** `Campaigns.ts:70-143` is untouched; the domain fakes' `getCampaign` over the `Map<string, Campaign>` keep returning full campaigns, so every `send`/`resume` comparison in `Campaigns.test.ts:316-399` and `Api.test.ts` stays as it is. The ADR's four-read consequence (line 36) matches the draft path (`get` at `:74` and `:86`, each now two reads) inside `Api.ts:33`'s 60 s. Holds.
