## Findings

### R1 — Medium: the plan walks into the zone's 86400 s negative cache twice

- **Where:** T2 _Preflight_ (`dig +short @8.8.8.8 … all empty`), T2 _Verify_ (the same names at `8.8.8.8`), T2 _Risk/recovery_ ("if status stays `PENDING` after the first hour, re-check the MX with `dig`"), and the T1→T2 order ("SES starts looking for the MX only after the attribute is set").
- **Evidence:** `dig SOA example.com` → `… 1209600 86400`: the zone's negative-caching TTL is 86400 s. This project already paid for that once: commit `50b5a93` ("the zone's negative-caching TTL is 86400 seconds … costs a day") and memory `dns-changes-stay-in-scope`. The precedent T3 (`sending-identity.md:141, :155`) preflighted through the Route 53 API and only ran `dig @8.8.8.8` after `INSYNC`. AWS's MAIL FROM page says SES "attempts to detect the required MX record for 72 hours" from the moment the attribute is set, and nothing there requires the attribute to exist before the records.
- **Realistic failure:** (a) The preflight digs `bounce.mail.example.com MX/TXT` and `_dmarc.mail.example.com TXT` at `8.8.8.8` and gets NXDOMAIN, which `8.8.8.8` may cache for up to a day; the T2 verify then shows nothing for hours after `INSYNC`, and the risk text invites "correcting" a record that is fine. (b) T1 sets the attribute while the MX does not exist; SES's first probe gets NXDOMAIN and its resolver may hold it under the same TTL, so `MailFromDomainStatus` sits at `PENDING` long after the records are visible everywhere, and the plan's "re-check with dig" step misdiagnoses it. Neither breaks the outcome (24 h < 72 h) but both produce false reds and, in case (a), a plausible operator error.
- **Smallest correction:** Preflight only through the APIs (`aws route53 list-resource-record-sets … --query` for the two names; Cloudflare API for `_report._dmarc`), never `dig` a name that is about to be created. Publish the three Route 53 records and poll `INSYNC` **before** T1's deploy (the DNS part of T2 moves ahead of T1; the SES status poll stays after T1). After `INSYNC`, verify against the zone's authoritative server first (`dig @<name server> …`), then `8.8.8.8`. Use `CREATE`, not `UPSERT`, in the change batch so a pre-existing record fails loudly. Replace the "first hour" heuristic with: authoritative answer correct → wait; SES's own resolver is not one you can flush.

### R2 — Medium: the gate assumes headers the receiver may not stamp

- **Where:** T3 _Tests_ ("`Authentication-Results` contains `spf=pass` with `smtp.mailfrom=`…", "`dmarc=pass` with `header.from=`…", "`Return-Path` (or the envelope sender in the first `Received` line)"); Research `:54` ("The operator mailbox is on Cloudflare, whose `Authentication-Results` carries the same three methods"); ADR-0010 _Confirmation_.
- **Evidence:** The operator mailbox is Email Routing delivering to an **Email Worker** (`the mailbox stack/alchemy.run.ts:116-121, 134-137`: `actions: [{ type: "worker" … }]`). Cloudflare documents that Email Routing records its verdicts in **`ARC-Authentication-Results: i=1; mx.cloudflare.net; dkim=… ; dmarc=pass header.from=… policy.dmarc=…; spf=pass (…) smtp.mailfrom=…`** (blog "Email Routing subdomain support, new APIs and security protocols"). An open `cloudflare/workerd` issue #6740 (May 2026) reports Worker-delivered messages with `Authentication-Results`, `Received`, `Received-SPF` **absent**. The only evidence in this repo (`sending-identity.md:189`) quotes `dkim=pass header.d=mail.example.com` and never an `spf=` or `dmarc=` token, so nothing on file shows this receiver reports SPF or DMARC. `Return-Path` is written by a final delivery agent; a Worker receives SMTP DATA, so it has no `Return-Path` to read.
- **Realistic failure:** T2 and T3 run, the message arrives, and the gate cannot be evaluated: no `spf=`/`dmarc=` token, no `Return-Path`, no `Received` chain. The operator either blocks with a good setup or "passes" on the DKIM token alone, which is exactly the false green the target is meant to exclude (DMARC passes on DKIM regardless of the new records).
- **Smallest correction:** Before any DNS write, read the 2026-09-14 message source that is still archived in the operator mailbox (`the mailbox CLI messages source --id …`) and record in the plan the exact header name and whether it carries `spf=… smtp.mailfrom=` and `dmarc=… header.from=` tokens (expected today: `spf=pass … smtp.mailfrom=…@amazonses.com`, `dmarc=none`, since no policy exists yet). Name that header in T3 (`ARC-Authentication-Results` if that is what it is). Replace the `Return-Path`/`Received` assertion with the operator mailbox's `envelopeFrom` field, which the inbound Worker archives from `message.from` and the API exposes (`the mailbox inbound handler:89`, `apps/api/src/projection.ts:132`), and which Worker delivery does not SRS-rewrite. If the archived message shows the receiver does not report SPF/DMARC verdicts, name the fallback receiver now (the Google Workspace address already in `EMAILER_ALLOWED_RECIPIENTS`) rather than discovering it after T2.

### R5 — Low: the `sp` rationale is wrong (decision is right)

- **Where:** Key files table, RFC 7489 row ("`sp` is ignored on a subdomain record").
- **Evidence:** RFC 7489 §6.3: `sp` is the policy for subdomains of the domain where the record is found. On `_dmarc.mail.example.com` it would govern From at `*.mail.example.com`, for example a spoofed `bounce.mail.example.com`. It is not ignored; it is simply unnecessary while `p=none`.
- **Smallest correction:** Reword to "no `sp`: with `p=none` the subdomain policy would add nothing yet".

## Verified claims

- **Alchemy provider.** `EmailIdentity.ts:62, :69` declare `mailFromDomain` / `mailFromBehaviorOnMxFailure` (default `USE_DEFAULT_VALUE`, "there is no removal path"). `diff` (`:275-284`) returns `replace` only on an identity-name change and `undefined` otherwise; `Plan.ts:1511-1519` then falls back to `havePropsChanged` (`Diff.ts:184-201`), and a new key in `news` is a change → `update`. Reconcile step 3e (`:371-386`) calls `putEmailIdentityMailFromAttributes` only when the observed domain or (when declared) behaviour differs; 3b/3c/3d are skipped because those props are undefined; `toAttributes` (`:199-211`) and `read` (`:260-273`) expose no MAIL FROM state. The "no-op redeploy does not restart a `FAILED` setup" claim follows from the same condition. `--detailed` exists (`Cli/commands/deploy.ts:62`; `plan` is a mode of the same command, `Cli/main.ts:37, :63`); `alchemy state read` exists (`Cli/commands/state.ts:125`).
- **AWS SES.** Exactly one MX `10 feedback-smtp.<region>.amazonses.com`; SPF TXT `v=spf1 include:amazonses.com ~all`; the MAIL FROM domain must be a subdomain of the identity and used neither to send nor to receive; states `Pending → Success/TemporaryFailure/Failed`, 72 h detection window, `Failed` requires restarting the setup; `USE_DEFAULT_VALUE` falls back to an `amazonses.com` subdomain, `REJECT_MESSAGE` raises `MailFromDomainNotVerified`. SPF-based DMARC compliance needs relaxed alignment (no `aspf=s`); the record lives at `_dmarc.<domain>`; `p=none` is the documented first step.
- **RFC 7489.** §7.1: the authorization record is `<policy-domain>._report._dmarc.<destination host>`, where the destination host is the host part of the `mailto:` URI (`reports.example.net`), not its Organizational Domain; `v=DMARC1` alone is sufficient. §3.1.2: relaxed SPF alignment = same Organizational Domain (`bounce.mail.example.com` ↔ `mail.example.com` share `example.com`). §6.3: `aspf` defaults to `r`. §6.6.3: `_dmarc.mail.example.com` is queried before `_dmarc.example.com`.
- **Zones.** `reports.example.net` has no delegation; its SOA answer comes from the `reports.example.net` zone on Cloudflare, so the TXT goes into that zone under the full name. Its MX is `route{1,2,3}.mx.cloudflare.net`. The mailbox stack declares Routing, Rules, CatchAll and SendingSubdomain resources and no DNS records (`alchemy.run.ts:110-145`), so a hand-added TXT survives redeploys. Authoritative `example.com` currently has no records at `bounce.mail.example.com`, `_dmarc.mail.example.com` or `_dmarc.example.com`, so the preflight would be clean today.
- **Cloudflare Email Routing.** Rejects mail that fails both SPF and DKIM and enforces the sender's DMARC policy (`p=none` rejects nothing); SRS rewrites the envelope only when forwarding to a destination address, not for Worker delivery, where `message.from` is the original envelope sender.
- **T3 is possible with today's code.** `.env.test` lists `dmarc@reports.example.net` first in `EMAILER_ALLOWED_RECIPIENTS`; `Campaigns.ts:97` enforces the allowlist and the single-member rule; the identical path ran on 2026-09-14 (`sending-identity.md:189-190`).
- **Independence.** Stage names `test-a`/`test-b` are distinct; the mass-sending plan does not touch `stacks/sending-identity.ts`, ADR-0002/0009/0010 or `wiki/aws/deliverability.md`; the reference reads only stables that T1 does not change.
- **Verification quality.** Asserting `spf=pass` **with `smtp.mailfrom` at the bounce subdomain** plus `header.from=mail.example.com` is the relaxed-alignment condition itself, so the plan does distinguish SPF pass from SPF alignment; `dmarc=pass` alone would not (DKIM carries it), and the plan does not rely on it alone. The DKIM timestamp check protects "nothing recreated". The remaining gap is R2: whether the receiver emits those tokens at all.
- **ADR-0002 and ADR-0009 corrections** are lifecycle links and clerical rewordings within the convention, except ADR-0009 `:29` (R4). ADR-0010 is `Proposed`, names its authority, and its alternatives and consequences match the plan.

## Verdict

**Changes required.** R1 and R2 are cheap to fix before implementation and each can turn a correct setup into a false red or a false green at the gate; R3–R7 are clerical.
