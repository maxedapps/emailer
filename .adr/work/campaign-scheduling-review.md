## Verified (no finding)

**The race trace.** Implemented as written, no fire is dropped silently, sent twice, or sent after cancel:

- **Fire on `scheduled`.** `beginRun`'s condition becomes `runToken = :run AND #state IN (:queued, :sending, :scheduled)`; the fire carries the token minted at schedule time; the write moves the item to `sending`, setting `queuedAt` and `startedAt` if absent. `if_not_exists(queuedAt, :now)` is correct because no path returns a campaign to `draft` with a `queuedAt`: `unscheduleCampaign` removes only `runToken` and `sendAt`, and a `scheduled` item only ever came from `draft` or `scheduled` (`Storage/Campaigns.ts:314-336, 360-404`; plan `:78-81`). The `sending` schema's required `queuedAt` (`Schemas.ts:210-213`; `Storage/Campaigns.test.ts:387`) is therefore satisfied on the fire path.
- **Cancel, then fire.** `unscheduleCampaign` writes `draft REMOVE runToken, sendAt`; a later fire evaluates `runToken = :run` against a missing attribute, which is false, so `beginRun` returns `stale` and `runSlice` returns (`Dispatching.ts:90-94`). Fire first, then cancel: `beginRun` wins, `unscheduleCampaign`'s condition (`#state = :scheduled OR (#state = :draft AND attribute_not_exists(runToken))`) fails, the domain returns the campaign as `sending`.
- **Send now, then fire.** `enqueueCampaign` admits `scheduled` and writes `queued` under a fresh token; the old fire is `stale`. Fire first: `enqueueCampaign` fails on `sending`, `send` returns the campaign. A `remove` that fails after the queued write answers 503 with the campaign `queued`; a repeated `send` takes `wakeQueued` (`Campaigns.ts:92-93, 105-119`) and the orphan schedule fires stale and deletes itself under `ActionAfterCompletion: DELETE`.
- **Reschedule, then old fire.** The second `scheduleCampaign` writes a fresh token; the old schedule's fire is `stale`; the new schedule (created after `remove` by name) fires once under the new token. Fire first: `scheduleCampaign` fails on `sending`, no schedule is created, the campaign is returned.
- **Duplicate fire.** Scheduler's at-least-once delivery is the SQS duplicate ADR-0011 already absorbs: the second `beginRun` sees `sending` under the same token and the slice re-walks from the checkpoint (`Storage/Campaigns.ts:554-583`).
- **Lost-response retries (ADR-0013).** Each new or changed condition holds after its own write for the actor that wrote it: `scheduleCampaign` (`scheduled` is in the set, same token and values), `unscheduleCampaign` (the `draft AND attribute_not_exists(runToken)` disjunct), `enqueueCampaign` from `scheduled` (the existing `queued AND runToken = :run` disjunct), `beginRun` (already qualified). The HTTP client does not retry (`packages/api/src/Client.ts` has no retry policy), so "the client retries every write" is the AWS client, and a human repeating `schedule` mints a new token and replaces — which the plan describes.

**Alchemy binding and role path.**

- `CreateSchedule(executionRole: Ro extends Role, group?: ScheduleGroup)` takes resource instances and returns a callable of `CreateScheduleRequest` with `GroupName`, `Target.RoleArn` and `FlexibleTimeWindow` injected (`CreateSchedule.ts:22-36, 101-118`; `BindingHttp.ts:165-218`). The deploy-time half grants `scheduler:CreateSchedule` on `arn:aws:scheduler:<region>:<account>:schedule/<group>/*` **and** `iam:PassRole` on the role with `iam:PassedToService: scheduler.amazonaws.com` (`BindingHttp.ts:174-197`); `DeleteSchedule(group?)` grants `scheduler:DeleteSchedule` on the same pattern (`BindingHttp.ts:100-121`; `DeleteScheduleHttp.ts`). `AWSEnvironment` is read only inside the `!__ALCHEMY_RUNTIME__` guard, as the wiki requires.
- `AWS.IAM.Role` accepts a props Effect: `ResourceConstructor` overload `(id, props: Effect<InputProps<Props>>)` (`Resource.ts:38-41`). An `Output<string>` inside `inlinePolicies[..].Statement[..].Resource` type-checks because `Input<T>` is deep (`Input.ts:21-28`: arrays map to `Input<T[number]>[]`, objects to `{ [K]: Input<T[K]> }`); `dispatchQueue` already relies on this for `redrivePolicy.deadLetterTargetArn: failures.queueArn` (`Dispatch.ts:32-47`).
- Yielding a resource inside the Function's init effect registers it: the repo's own `AWS.SQS.SendMessage(yield* dispatchQueue)` at `Api.ts:184` carries the comment "Yielding the source queue registers it" and is proven live; `alchemy.run.ts` never yields `dispatchQueue` itself (`alchemy.run.ts:22-29`). `yield* schedulerRole` and `yield* scheduleGroup` follow the same path.
- `Target.Arn: yield* queueArn` at runtime resolves: yielding an `Output` calls `bind`, which registers the key on the `RuntimeContext` at deploy and reads it back at runtime (`Output.ts:142-163`); the `CreateSchedule.ts:80-87` example uses exactly this form, and the binding resolves `RoleArn` and `GroupName` the same way (`BindingHttp.ts:169-170, 206-207`).
- `ScheduleGroup("Schedules")` with no props is valid (`ScheduleGroupProps` all optional; `Resource.ts:34-36`); its delete is `deleteScheduleGroup` with `ResourceNotFoundException` swallowed (`ScheduleGroup.ts:263-271`); the physical name is `${app}-${id}-${stage}-<instance suffix>` (`PhysicalName.ts:13-28`). AWS deletes the group's schedules with the group (plan's quoted [DeleteScheduleGroup](https://docs.aws.amazon.com/scheduler/latest/APIReference/API_DeleteScheduleGroup.html) text). `CreateScheduleHttp` and `DeleteScheduleHttp` are exported from `alchemy/AWS` (`Scheduler/index.ts`; `AWS/index.ts:187`).
- The execution role's `sqs:SendMessage` on `queue.queueArn` is sufficient: the queue has SQS-managed SSE and no resource policy (`Dispatch.ts:32-47`), so a same-account role with the identity grant may send.

**distilled client claims.**

- `CreateScheduleInput.ClientToken` is `S.optional(S.String).pipe(T.IdempotencyToken())` (`services/scheduler.ts:413`), and `fillIdempotencyTokens` only fills a property that is `=== undefined` (`client/generate-idempotency-tokens.ts:71-78`), so a supplied `runToken` is sent verbatim. A UUID v4 fits `ClientToken`'s `[a-zA-Z0-9-_]+`, max 64, and `Name`'s `[0-9a-zA-Z-_.]+`, max 64 (CreateSchedule reference, fetched). The "fresh token per attempt when not supplied" half is ADR-0013's recorded finding and was not re-verified here; it is not load-bearing once the token is supplied.
- `ResourceNotFoundException` is a `TaggedError` with that exact tag and is a member of `DeleteScheduleError` (`services/scheduler.ts:109-114, 970-988`), so `Effect.catchTag("ResourceNotFoundException", ...)` is the right tag — and is the form Alchemy's own `DeleteSchedule` doc and `ScheduleGroup` provider use (`DeleteSchedule.ts:24-27`; `ScheduleGroup.ts:97-99`). `ExecutionRoleNotAssumable` is synthesised from a `ValidationException` whose message contains "must allow AWS EventBridge Scheduler to assume the role" (`:92-102`), so it is catchable by tag if ever needed.

**Effect compositions (type-checked against the installed Effect with the repo's `tsconfig.base.json`, executed under `TZ=Europe/Berlin`).**

- `Flag.string("at").pipe(Flag.withDescription(...), Flag.withSchema(Schema.DateTimeUtcFromString), Flag.map(DateTime.formatIso))` yields `Flag<string>` and composes into `Command.make` — compiled.
- `Schema.TaggedError<SendAtNotInFuture>()("SendAtNotInFuture", { sendAt: Timestamp }, { httpApiStatus: 409 })` compiles and serialises as `{"_tag":"SendAtNotInFuture","sendAt":"..."}`; the two planned endpoints with their error lists compile inside an `HttpApiGroup`; `Effect.retry(..., { while, schedule: Schedule.spaced("5 seconds"), times: 12 })` compiles; the `scheduled` union member compiles.
- `DateTimeUtcFromString` decodes `2026-09-20T09:00`, `2026-09-20T09:00Z` and `2026-09-20 09:00` to `2026-09-20T09:00:00.000Z`, `2026-09-20` to midnight UTC, `2026-09-20T09:00+02:00` to `07:00:00.000Z`, and refuses `nonsense`; `new Date("2026-09-20T09:00")` under the same `TZ` gives `07:00:00.000Z`, which is the plan's `Flag.date` objection (`Flag.ts:130`: `Param.date`). `DateTime.formatIso` renders the `.sssZ` form `Timestamp` requires (`Schemas.ts:59-67`). `"2026-09-20T09:00:00.000Z".slice(0, 19)` is `2026-09-20T09:00:00`.
- `HttpApiClient` keys error decoders by status and accepts several schemas per status (`HttpApiClient.ts:276, 338-347`), and the contacts `update` endpoint already declares two 409s (`packages/api/src/Api.ts:70-74`); the `schedule` endpoint has only one 409 anyway, so the CLI decodes `SendAtNotInFuture` beside `NotFound`, `StorageUnavailable` and `BadRequestNoContent`.

### Verified (no finding)

- **Item 1, `queuedAt` as the instant.** `beginRun`'s update is `SET #state = :sending, startedAt = if_not_exists(startedAt, :now)` (`Storage/Campaigns.ts:367`), so a fired campaign decodes as `sending` with `queuedAt` = the scheduled instant and `startedAt` = the dispatcher's `nowIso` at the fire (`Dispatching.ts:90`). That satisfies the "sending without `queuedAt` is corrupt" rule (`Storage/Campaigns.test.ts:387`). A draft never carries `startedAt`, `cursor` or `runToken`: create writes none of them (`:208-245`), and `unscheduleCampaign` removes `runToken` and `queuedAt`. So `if_not_exists(startedAt, ...)` records the fire, and `enqueueCampaign`'s unchanged expression on a scheduled campaign overwrites `queuedAt`, `runToken` and the three baselines with nothing stale left. `resumeCampaign` (`:338-358`) still admits only `paused`/`queued`. Outside `Storage/Campaigns.ts`, `queuedAt` is read only in the contract schema and test fixtures. The five `switch` sites on state are the domain's `send`/`resume` (default arm), `submissionOf` (gains the case), `settlementWrite` (unrelated) and `IntegrationSupport.ts:366` (default arm). No production reader misreads a scheduled campaign.
- **Repeat-safety (ADR-0013).** ADR-0013 covers the AWS client resending the identical request. `scheduleCampaign`'s resend carries the same token and instant, and `#state IN (:draft, :scheduled)` holds after its own write. `unscheduleCampaign`'s `IN (:scheduled, :draft)` holds after its own write and is safe unqualified, because a draft never holds a token. An operator repeating `schedule` mints a new token and replaces the schedule, which ADR-0013's "a human retrying ... gets a new entity" already frames. `ClientToken = runToken` can recur only inside the distilled client's per-call retry of `createSchedule`. The `remove`-then-`create` adapter is never re-run under the same token, because every domain call mints a fresh one, so an idempotent replay can never follow a `remove` that deleted the schedule it would replay.
- **Item 2, T7's assertion.** For a whole-minute `at()` AWS documents invocation within that minute's 60 seconds, and `startedAt` is written after the SQS hop from the Lambda clock, so `startedAt >= sendAt - 1000` holds. The 1 s slack absorbs runner/Lambda clock skew. Timing: `sendAt` is at most 150 s ahead, plus at most 59 s precision, inside `campaignStateTimeout(2, rate) + 3 min` = 360 s (`IntegrationSupport.ts:37`), inside `sendTestTimeout` 480 s.
- **Item 3.** Effects are lazy, so passing `client.campaigns.schedule({...})` as the submitting effect runs it only after the member walk (`IntegrationSupport.ts:239-252`). Feasible as described.
- **Item 4, `Dispatch.ts`.** It already imports `* as AWS from "alchemy/AWS"`. Resource constructors return an `Effect` (`Resource.ts:24-41`) that registers only when yielded. `Dispatcher.ts` imports `decodeDispatchMessage`, `dispatchQueue`, `encodeDispatchMessage` (`:9`) and yields only `dispatchQueue` (`:61`), so the dispatcher neither registers nor binds the role or group. The API function yields them, as it already yields `dispatchQueue` (`Api.ts:184`). The leaf comment forbids a Function class, not a Role or group.
- **Item 5.** `SendAtNotInFuture` is stated as a contract rule in plan :13, :54 and ADR :21, consistent with the DEX-004 disposition (R2 and R3 aside).
- **Leftovers.** No remaining `sendAt` attribute, `REMOVE sendAt`, `Scheduling.ts`, `attribute_not_exists(runToken)` or `Effect.retry` in either target. The remaining "wait a minute and repeat" (:51, T3 :108, ADR :40) is operator guidance, which DEX-003 recommended keeping.

**The one question.** Implemented as written with every named check green:
- **Not dropped silently.** T2's `:scheduled` admission closes the `stale` return at `Dispatching.ts:90-94`, and T7 proves it live. The residual paths leave the campaign visibly `scheduled` with `send` as the documented recovery: an undeliverable fire, a crash between write and create, and R9's concurrent reschedule.
- **Not sent twice.** A duplicate fire re-enters under the same token and re-walks from the checkpoint. A send-now writes a fresh token, and the old fire is stale.
- **Not sent after cancel.** `REMOVE runToken` makes `runToken = :run` false. A fire that wins the race moves the item to `sending`, `unscheduleCampaign`'s condition fails, and cancel answers `sending`.
- **Not sent before its minute.** For a whole-minute `sendAt`, AWS documents the window as that minute. For a mid-minute instant the plan now promises only "the minute of `sendAt`", which is exactly what the documentation supports and what T7 records.
