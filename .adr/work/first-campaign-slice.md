## Outcome and boundaries

Build a working CLI flow that creates a contact, creates a list, adds the contact, creates a campaign targeting that list, submits its literal plain-text message to SES, and retrieves the persisted result. The sending guard permits exactly one list member whose email matches the configured recipient. The intended real recipient is the owner of this project.

**In scope:** authenticated Lambda Function URL; Effect HTTP contract/client; contact/list/campaign creation and ID-based retrieval; idempotent membership addition; one synchronous submission per campaign; persisted acceptance, rejection or uncertainty; useful CLI errors; local tests and an ephemeral AWS `test` deployment.

**Out of scope:** queues, scheduling, background processing, automatic resend/recovery, bulk delivery, bounce/complaint/delivery processing, unsubscribe, tracking, HTML, placeholders/personalization, contact import, editing/deleting entities, search, listing all campaigns/contacts, MCP implementation, admin UI, Cognito, API Gateway, external auth frameworks and production rollout. Real newsletter sending remains prohibited until subscription and feedback handling exist. Lambda execution/deployment IAM is still required; HTTP callers use the shared token.

**Approach:** capability-owned infrastructure under the backend source tree, a small Stack, one DynamoDB table and one Lambda. Source-level sharing stays inside the owning app. Keep the pinned toolchain and compatibility fixes; do not upgrade dependencies as part of this slice.

## Research and implementation constraints

- Installed baseline: Alchemy `2.0.0-beta.77`, Effect/platform-node `4.0.0-rc.112`, Distilled AWS/core `1.0.0-rc.9`, TypeScript `7.0.2`, Vitest `5.0.0`, Node `24.19.0`. Keep catalog/lockfile compatibility overrides. Add `alchemy: catalog:` to backend direct dependencies because its source will import it.
- Alchemy service Layers can encapsulate resources and bindings. Supply operation implementation Layers privately with `Layer.provide`; use `Layer.mergeAll` for independent services. A shared table declaration must not be reconstructed with conflicting props under the same logical ID. [Layers](https://alchemy.run/infrastructure-as-effects/layers/), [file layout](https://alchemy.run/project-structure/file-layout/)
- `Api.ts` uses Effect-mode `AWS.Lambda.Function`, `main: import.meta.url`, `functionUrl: { authType: "NONE" }`, and `{ fetch: ... }`. The provider uses a generated native entry; do not specify a handwritten `handler` export. Timeout is an Effect `Duration`. Resolve app Config during construction, not only in handlers. [Pinned Function source](https://unpkg.com/alchemy@2.0.0-beta.77/src/AWS/Lambda/Function.ts), [phases](https://alchemy.run/infrastructure-as-effects/phases/)
- RC112 HTTP uses `effect/unstable/httpapi` and `effect/unstable/http`. `HttpRouter.toHttpEffect` needs a construction Scope and produces a handler needing the invocation Scope. Capture production capabilities/config during Lambda initialization, then construct and execute the router within each invocation's Scope, using captured capability values rather than reconstructing resource-owning Layers. Never return a handler from a closed `Effect.scoped` region. Explicitly satisfy `HttpPlatform` and `Etag.Generator` using NodeHttpPlatform/Etag Layers alongside available Node services; do not launch a listening NodeHttpServer. [Pinned HttpApiBuilder](https://unpkg.com/effect@4.0.0-rc.112/src/unstable/httpapi/HttpApiBuilder.ts), [HttpRouter](https://unpkg.com/effect@4.0.0-rc.112/src/unstable/http/HttpRouter.ts), [NodeHttpPlatform](https://unpkg.com/@effect/platform-node@4.0.0-rc.112/src/NodeHttpPlatform.ts)
- Beta.77 Lambda has no log-retention property. An `AWS.Logs.LogGroup` declaration in `Api.ts` owns the conventional `/aws/lambda/<functionName>` group and its retention. Model its dependency and initialization before first invocation; do not invent a Lambda option. [Pinned LogGroup](https://unpkg.com/alchemy@2.0.0-beta.77/src/AWS/Logs/LogGroup.ts)
- DynamoDB bindings accept raw AttributeValue objects; isolate encoding/decoding in Storage. `TransactWriteItems(table)` items use `Table: table.LogicalId`, not `TableName`. Use stable, unique `ClientRequestToken` values per transaction invocation; SDK retries must reuse identical parameters. Durable campaign conditions remain necessary after the AWS token's ten-minute window. [Pinned transaction binding](https://unpkg.com/alchemy@2.0.0-beta.77/src/AWS/DynamoDB/TransactWriteItems.ts), [AWS transactions](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html)
- Distilled retries transient calls by default. Wrap the actual SES invocation with the pinned `Retry.none` policy; its operation implementation merges per-call context over captured context. Prove this with a transport test rather than assuming a service fake proves one attempt. Do not disable harmless deployment/read retries globally. [Pinned retry module](https://unpkg.com/@distilled.cloud/aws@1.0.0-rc.9/src/retry.ts), [operation context and retries](https://unpkg.com/@distilled.cloud/core@1.0.0-rc.9/src/api.ts)
- SES `MessageId` proves acceptance, not delivery. `SendEmail` has no client idempotency key, and a database transaction cannot atomically include sending an email. [SES SendEmail](https://docs.aws.amazon.com/ses/latest/APIReference-V2/API_SendEmail.html)
- Function URLs with `NONE` require application authentication and the appropriate invoke permissions. Check the generated policies as part of deployment validation. [AWS URL authorization](https://docs.aws.amazon.com/lambda/latest/dg/urls-auth.html)
- Node 24 supports erasable TypeScript directly but ignores tsconfig aliases and refuses TS under real `node_modules` paths. The local CLI relies on normal real-path resolution of pnpm workspace links, explicit file extensions and type-only imports; verify the actual process, not only Vitest's bundler. No `--preserve-symlinks` or TS files published into dependencies. [Node TypeScript support](https://nodejs.org/docs/latest-v24.x/api/typescript.html)

## Proposed application contract

These are concrete implementation defaults within the agreed scope. No client can choose an arbitrary sender, disable the allowlist, force a resend or write send status.

| HTTP operation                          | CLI operation                                           | Observable behavior                                                                    |
| --------------------------------------- | ------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `POST /contacts`                        | `contacts create --email ... --name ...`                | Create immutable contact, return ID and record; 201                                    |
| `GET /contacts/:id`                     | `contacts get <id>`                                     | Retrieve contact; 200 or 404                                                           |
| `POST /lists`                           | `lists create --name ...`                               | Create list; 201                                                                       |
| `GET /lists/:id`                        | `lists get <id>`                                        | Retrieve list metadata; 200 or 404                                                     |
| `PUT /lists/:listId/members/:contactId` | `lists add-contact <listId> <contactId>`                | Require existing contact/list; repeated addition is a no-op; 204                       |
| `POST /campaigns`                       | `campaigns create --list <id> --subject ... --text ...` | Require existing list; create immutable draft; 201                                     |
| `GET /campaigns/:id`                    | `campaigns get <id>`                                    | Retrieve content and authoritative campaign submission status; 200 or 404              |
| `POST /campaigns/:id/send`              | `campaigns send <id>`                                   | Validate/claim/submit once, or return existing attempt status without submitting again |

IDs are server-generated UUIDs. Names are trimmed nonempty strings up to 200 characters; contact name is optional. Email addresses use an explicit ASCII mailbox subset, trimmed, with the domain lowercased and local part preserved; compare the parsed address exactly against the similarly normalized allowlist value. Do not claim SMTPUTF8 support. Subjects must be nonempty, single-line, at most 200 characters. The body is nonempty literal text up to 64 KiB UTF-8; retain its whitespace and line breaks. Reject CR/LF in header fields. Cap the HTTP request body at 512 KiB before unbounded buffering/JSON decoding; escaped JSON must still be constrained by the decoded text limit. Bound every persisted record below DynamoDB's 400 KiB maximum. Unknown request properties cannot become stored/internal fields.

No uniqueness promise for contact email or list name in this slice: identity is by ID. Duplicate IDs in a list cannot occur; two separate contacts are two members even if they share an email and therefore fail the one-member guard. Create operations have no automatic client replay; membership PUT and campaign send replay behavior are explicitly defined above.

All routes require a single `Authorization: Bearer <token>`. Token format is 32 random bytes encoded as base64url (43 characters); parsing honors case-insensitive header/scheme but case-sensitive token. Reject malformed, duplicate/comma-joined or wrong credentials with generic 401 and a Bearer challenge before body decoding or service operations. Use equal-length `timingSafeEqual`; fail initialization if token config is absent/malformed. No CORS configuration or public status route is necessary for CLI access. Enforce the request-byte cap explicitly when reading the body, including when Content-Length is absent; supplying Effect's MaxBodySize alone does not constrain RC112's Web Request `.text` path. Oversize input returns 413 with no operation side effects.

Validation errors are 400, missing entities 404, changed state/membership conflicts 409, and invalid audience 422. Provider/storage failures use bounded public error schemas with operation IDs, never raw AWS exceptions or secrets. A durable accepted/rejected result is returned as a submission result; the CLI exits zero only for acceptance. Unconfirmed outcomes return a typed 503 on the initiating send; replay can return the stored unconfirmed status with no new side effect. `GET` remains available for inspection. CLI emits machine-readable JSON on stdout, diagnostics on stderr, and nonzero on parser/auth/transport/rejection/unconfirmed failure.

## DynamoDB records and submission protocol

Use one on-demand table with string `pk` and `sk`, stable logical ID `EmailerData`. No GSI, TTL, streams, member counter or outbox. IDs and ISO UTC timestamps are generated before constructing retried write payloads. Use schema version 1 on persisted entity records and validate reads; corrupt data is a typed storage error.

| Partition / sort key                 | Contents                                                                                                                     |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| `CONTACT#<id>` / `META`              | ID, email, optional name, createdAt                                                                                          |
| `LIST#<id>` / `META`                 | ID, name, createdAt, monotonic membershipVersion initially 0                                                                 |
| `LIST#<id>` / `MEMBER#<contactId>`   | Contact ID and addedAt                                                                                                       |
| `CAMPAIGN#<id>` / `META`             | ID, listId, subject, text, createdAt, state, submission metadata                                                             |
| `CAMPAIGN#<id>` / `SEND#<contactId>` | Unique sendId, contactId, frozen recipient/from/subject/text, state, startedAt, optional finishedAt/messageId/rejection code |

Creation uses conditional Put to avoid overwriting another record. Membership addition uses a transaction: existing-contact check, existing-list version increment and absent-member Put. If the membership already exists, return success without incrementing the version; distinguish missing parents and genuine transaction failure through cancellation reasons or authoritative rereads. There are no contact edits or entity deletions in this slice.

Campaign GET reads the campaign metadata as its authoritative status; it need not join a separately read send record and promise an atomic snapshot. The send record preserves independent per-recipient history for later expansion.

Use the small durable state machine **`draft → unconfirmed → accepted | rejected`**. `unconfirmed` means an attempt has been reserved but its outcome is not durably established. It can represent an active invocation or an interrupted one; it never promises that work is still running. Every non-draft state blocks another submission forever in this slice. There is no lease, expiry, automatic reset or retry command.

1. Read the draft campaign and list metadata strongly consistently. Query the base table for the list's `MEMBER#` keys without a filter; paginate until zero, exactly one, or a second member is established. Fetch the immutable contact and validate the configured recipient. Invalid audience leaves the campaign draft and performs no SES call.
2. Claim atomically: check the unchanged membershipVersion, change campaign from draft to unconfirmed, freeze the submission configuration/content, and create its unconfirmed recipient send record with an absent-key condition. This prevents both competing send requests and a membership change between enumeration and claim. A changed version returns conflict; do not add a retry loop.
3. Only an acknowledged winning claim can call SES. If the claim response is lost, do not infer ownership and send; return uncertainty. If another request already claimed the campaign, read and return its existing status, without submitting.
4. Submit one SES v2 Simple message with one To address, explicit From and UTF-8 subject/text, the bound configuration set and opaque campaign/send correlation tags. Apply operation-local no-retry and a bounded timeout.
5. A response with MessageId is acceptance. Transactionally finalize campaign and recipient records to accepted, conditional on the same sendId and unconfirmed state. A recognized definitive SES rejection finalizes both to rejected with a safe error code. Opaque server/transport errors, interruption, malformed acceptance responses and timeouts remain unconfirmed.
6. Handle final persistence separately from SES submission. If SES accepted/rejected but the final transaction acknowledgement is lost, return a status-persistence error with campaign/send IDs; the stored state may already be terminal or still unconfirmed. Never translate this into a definitive SES rejection or resend. GET resolves whatever was durably stored. A hard crash can leave unconfirmed indefinitely.

The invariant is **no second application submission after a durable claim**, with explicitly possible zero-send stranded claims. This is not exactly-once delivery. Fixing/recovering a rejected or uncertain campaign is deferred; operators must inspect evidence before deliberately creating a different campaign.

## Configuration and lifecycle

Required application values: `EMAILER_API_TOKEN` (redacted), `EMAILER_FROM_EMAIL`, and `EMAILER_ALLOWED_RECIPIENT`. CLI also needs `EMAILER_API_URL`. First-slice sender identity is a single email address equal to FROM, keeping domain/DNS automation out of this implementation. Alchemy profile/account/Region and stage are explicit deployment inputs, not guessed defaults. Test values live outside Git in `.env.test`; `.env.example` documents keys with no usable secrets.

Mailer owns logical IDs `EmailerSender` and `EmailerMail`; the latter is a configuration set with no tracking/event destinations. Api owns logical IDs `Api` and `ApiLogs`, Node 24, a 30-second Lambda timeout, a LogGroup with seven-day retention and a Function URL. Keep the function/group naming dependency local to `Api.ts`; use one stable stage-specific function name and ensure the matching group is ready before invocation. Bound read/write operations must have time budgets, SES submission at most 8 seconds, and finalization at most 5 seconds. Track an application request deadline with Effect Clock, leaving enough budget before claiming for submission and finalization; do not assume Alchemy exposes native Lambda getRemainingTimeInMillis to domain code. CLI total request timeout exceeds the Lambda budget (40 seconds). Do all required writes before returning; no detached fibers/promises.

Set application data/sender retention for non-test stages deliberately; `test` resources are destroyable. Source moves preserve logical IDs. First test deployment requires a **dedicated new email alias** that can receive SES's verification message; preferably use the same owned alias for sender and allowed recipient so one verification suffices. Preflight must establish that the identity is not already owned by another workload. Do not adopt or destroy an existing identity, change account-global SES settings, or set an identity's default configuration set. An already managed cross-stage identity reference is a possible future alternative, not another mode to implement now.

Account/Region credentials, the dedicated test address and verification are execution prerequisites, not architecture decisions left for the implementer. Collect them before T8. The repository authorizes ephemeral test deployments during implementation; this plan-writing task performs none. Cloud validation is incomplete until sending and cleanup are observed. Alchemy `plan` can bootstrap remote state: it is not a cloud-free lint command.
