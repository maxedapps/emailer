## Outcome and boundaries

- **Problem and target:** The service can send, but nothing consumes what happens next. The configuration set is created bare, so bounces and complaints go nowhere, no suppression state exists, and a hard-bounced address would be mailed again forever. The [first slice plan](first-campaign-slice.md) states that "real newsletter sending remains prohibited until subscription and feedback handling exist". This slice delivers the feedback half: SES bounce and complaint events are durably recorded, a hard-bounced or complained address is suppressed, and a suppressed address is refused before any SES call.
- **In scope:** a configuration set event destination publishing `BOUNCE` and `COMPLAINT` to the default EventBridge bus; SES's own suppression enabled for our configuration set; a second Lambda that consumes those events, classifies them and writes address-keyed suppression plus bounce/complaint history with idempotent conditional writes; a send guard that refuses a suppressed recipient; a widened but still explicit recipient allowlist so the mailbox simulator can drive both event paths; unit tests plus a live ephemeral `test` verification using the mailbox simulator.
- **Out of scope:** unsubscribe and `List-Unsubscribe` (RFC 8058), consent/opt-in state, bulk fan-out, SQS, scheduling, open/click tracking, HTML, un-suppressing or resubscribing a contact, SES multi-tenancy, a dead-letter queue, a reconciliation sweep over SES's suppression list, `DELIVERY` events, CloudWatch alarms, listing or searching contacts, and production rollout. **Replacing the recipient allowlist with an open contact list is explicitly deferred** — see the non-goal note below.
- **Approach:** one new capability module owning one new Lambda, per [ADR-0001](../0001-resource-owning-effect-services.md). No new table: suppression and feedback records are new item types in the existing single-table design. Suppression is keyed by the **lowercased email address**, not the contact ID, which matches the event payload, matches SES's own model, and avoids a secondary index.

**Named non-goal, recorded as the expected next work:** the send guard still permits only a list member whose address is in a configured allowlist. Opening that to an arbitrary contact list is wanted soon, but it must follow feedback/suppression and consent/unsubscribe — opening the recipient set before bounces can be suppressed is the sequence that damages sending reputation. When it happens it warrants its own ADR rather than an edit to the guard, because it is the point at which the system becomes able to mail arbitrary real people.

## Research

Findings that shaped the design. Sources are the installed Alchemy 2.0.0-beta.77 source and current AWS documentation.

**SES → EventBridge is best-effort, not at-least-once.** The EventBridge reference for SES gives its delivery type as "Best effort": "the service attempts to send all events to EventBridge, but in some rare cases an event might not be delivered", as opposed to durable delivery, which is at-least-once. SES also states events "might be delivered out of order" and makes no ordering or batching guarantees. **Events can be silently lost before reaching the bus.**

**How a lost event heals, and why there is no reconciliation sweep.** T3 enables SES-side suppression for our configuration set, so when an address hard-bounces SES suppresses it whether or not our event arrives. If the event is lost, our local record is missing and the next send to that address is not refused. That send then reaches SES, which "accepts the message, but doesn't send it" and emits an echo our classification **does** suppress: a bounce with subtype `OnAccountSuppressionList` for a bounce-suppressed address, or a complaint with `complaintSubType: "OnAccountSuppressionList"` for a complaint-suppressed one. So a lost event self-heals on the next send attempt, at the cost of one wasted SES call. This is why the plan carries no reconciliation sweep over `ListSuppressedDestinations`: the sweep would need a new HTTP endpoint (ADR-0001 forbids the CLI importing backend code, and the feedback Lambda has no Function URL), would page an account-wide list shared with any other SES sender on the account, and would pull third-party recipient addresses into our table — all to buy what the echo already provides. The residual cost is recorded in Final acceptance.

**No dead-letter queue.** Two distinct loss modes exist, and they need separating. SES-side loss (best-effort publication) is not addressable by a DLQ under any composition. Post-bus loss — a handler that fails until EventBridge's 24-hour retry budget is exhausted — _is_ addressable, and `consumeEmailEvents` cannot reach it: the helper calls `createLambdaRoute(descriptor, host)` with no target props, so `RetryPolicy` and `DeadLetterConfig` are unreachable. A composition using `AWS.EventBridge.events(...).toLambda(fn, { DeadLetterConfig })` **would** reach it, at the cost of a queue, a policy and a drain path. We judged that disproportionate for this slice and instead removed the ways a handler can fail permanently: anything unrecognised is logged and succeeds (see T4), so the realistic remaining causes are transient.

**`consumeEmailEvents`'s `configurationSets` option is unusable in this version.** It builds the correct server-side rule pattern, but the in-Lambda re-check compares the expected string against `detail.mail.tags["ses:configuration-set"]`, which is an **array**; `matchValue` (`EventBridge/EventSource.ts:156-172`) unwraps only the expected side, so the comparison is `["..."] === "..."` → `false`. The listener then returns nothing, the runtime throws "No event handler found" (`Lambda/Function.ts:1100`), and the invocation fails. The option is also typed as plain `string`, not `Input<string>`, so the generated physical name could not be passed anyway. **Filter inside the handler.** Note the helper always sets `detail-type` from `kinds`, so account-level Virtual Deliverability Manager events never reach us; the handler filter exists solely because the pattern does not constrain the configuration set.

**The tag carries the physical name, not the logical ID.** `ses:configuration-set` holds Alchemy's generated physical name. The feedback function must therefore obtain that name from the exported `ConfigurationSet` declaration and pin it into its own `env`. Re-declaring the resource inline in a second module to read the name is a trap: registration is idempotent by fully-qualified name and **the first registration site's props win**, with `Resource.ts:397` carrying an unimplemented `TODO` for exactly this. A second bare `ConfigurationSet("EmailerMail", {})` registered first would silently discard T3's `suppressedReasons`.

**Three vocabularies for the same events**, which must not be confused:

| API `matchingEventTypes` | EventBridge `detail-type`  | `detail.eventType` |
| ------------------------ | -------------------------- | ------------------ |
| `BOUNCE`                 | `Email Bounced`            | `Bounce`           |
| `COMPLAINT`              | `Email Complaint Received` | `Complaint`        |

**Classification.** The rule is deliberately coarse, because SES-side suppression already governs delivery and local classification only governs whether we refuse _before_ the call. Every exception we might add would make the local rule looser than SES's, and the outcome of each would be identical: SES accepts, does not send, and emits an echo bounce. So:

- `bounce.bounceType === "Permanent"` ⇒ suppress. This deliberately **includes** the echo subtypes `Suppressed`, `OnAccountSuppressionList`, `OnTenantSuppressionList` and `EmailValidationSuppressed` — recording them is what makes the self-healing above work. Declining to record them would guarantee we call SES again on every subsequent send, forever.
- `Transient` (including `MailboxFull`) ⇒ never suppress.
- `Undetermined` ⇒ never suppress. AWS documents no handling for it; it is the only `Undetermined/Undetermined` combination, and hard-bounce-only matches SES's own rule.
- `Complaint` ⇒ suppress, unless `complaintFeedbackType` is `not-spam` (the reporter explicitly does not consider it spam) or `auth-failure` (a DMARC/DKIM authentication report about our own sending, not a recipient complaint). The field is **optional**; absent still suppresses. This deliberately includes the complaint echo `complaintSubType: "OnAccountSuppressionList"`, which carries no feedback report and so arrives with `complaintFeedbackType` absent: **recording it is what makes self-healing work for complaint-suppressed addresses**, exactly as the `Permanent` echo subtypes do for bounces. Do not add a third exception for it.
- Persist `bounceSubType`, `complaintFeedbackType` and `complaintSubType` on the record for diagnostics without branching on them.

Complaint events only arrive from providers with a feedback loop, so they are a floor, never a complete picture; Gmail supplies none.

**Deduplication.** `bounce.feedbackId` and `complaint.feedbackId` are documented unique IDs and are the dedup keys. The EventBridge envelope `id` only dedupes target-invocation retries. `mail.messageId` alone is insufficient because one message legitimately produces several events.

**Correlation.** Custom tags appear at `detail.mail.tags.<name>` as an **array of strings**, so `campaignId[0]`. Tags are published only through configuration-set event publishing — identity-level notifications carry none, so that second path must not be enabled.

**Alchemy wiring, verified against source.** `AWS.Lambda.EventSource` (`AWS/Lambda/EventBridgeEventSource.ts:111`) must be provided on the Function init effect and only works inside init. The rule resolves to the account default bus automatically when no bus is given, but `eventBridgeDestination.eventBusArn` is required and must be built explicitly — Alchemy's own code uses `` `arn:aws:events:${region}:${accountId}:event-bus/default` `` from `AWS.AWSEnvironment.current`, free inside Function init. One event is delivered per invocation. The handler's requirements are erased by a cast at `EventBridgeEventSource.ts:151`, so `Effect.provide` of capabilities is mandatory — the type checker will not catch a missing service.

**Resource sharing.** Registration is idempotent by fully-qualified name (`Resource.ts:358-398`), and Function init pushes no namespace, so both Functions yielding the exported `dataTable` receive the identical resource. IAM is per-host, so each Function gets its own role and grants. Both Functions must be yielded from the Stack generator or they are never registered. **No Lambda in this slice calls any SES suppression API.** With the reconciliation sweep removed, the feedback function binds only `Storage`; the configuration set and its event destination are deploy-time resources, not runtime bindings. The feedback role should therefore contain DynamoDB access to the table plus basic execution and **no SES actions at all**.

**Mailbox simulator.** Simulator mail does not affect reputation metrics or the daily sending quota, is still rate-limited, and **is billed normally**. `bounce@simulator` is documented as _not_ being added to SES's suppression list — but that exemption is stated only for the bounce address. Nothing exempts `complaint@simulator`, and T3 enables `COMPLAINT` suppression, so a complaint test would otherwise add a permanent entry to the shared account list. T7 therefore uses label addressing (`complaint+<runId>@simulator.amazonses.com`) and checks for leftovers at teardown. AWS does not document which `bounceType`/`bounceSubType` the simulator produces, so T7 records the observed values; the coarse `Permanent` rule above does not depend on the subtype.

#### T2 — Persist suppression and bounce/complaint history

- **Change:**
  - Add a **suppression-only** key builder that fully lowercases the address, and use it on both the write and the read. This is deliberately different from `normalizeEmailAddress`, which preserves local-part case: the address in a bounce payload comes from the receiving MTA's DSN `Final-Recipient` and is not guaranteed to match the case we sent. SES itself "treats addresses with different cases as identical" when sending, so a case-insensitive key matches the behaviour we are guarding.
  - Add the suppression record: `pk = SUPPRESSION#<lowercased email>`, `sk = SUPPRESSION`, carrying reason, the originating `messageId` and `feedbackId`, the raw `bounceSubType`/`complaintFeedbackType`/`complaintSubType` for diagnostics, and a timestamp.
  - Add `suppressAddress(...)` writing that record conditionally, with an **explicit** `Effect.catchTag("ConditionalCheckFailedException", …)` that resolves to success. Do not reuse `createRecord` (`Storage.ts:174-181`), which maps every failure including a conditional failure to `StorageFailure{reason:"unavailable"}`. Suppression is **monotonic**: first write wins, nothing in this slice removes it.
  - Add `isAddressSuppressed(email)` returning the record as an `Option`, using the same lowercased key.
  - Add the history record: `pk = CAMPAIGN#<campaignId>`, `sk = FEEDBACK#<eventType>#<feedbackId>`, written with the same conditional-is-success handling so a redelivered event is a no-op.
  - **Suppress first; write history only when a `campaignId` tag is present.** The suppression record is address-keyed and needs no campaign, so the safety-critical write must never be gated on a field that only the history record requires. No unattributed partition: every send tags `campaignId`, so a missing tag cannot occur in practice and is logged.
  - History is what gives the `Transient` and `Undetermined` outcomes any effect at all: those events suppress nothing, so without a record they would be only a log line. It is also the only durable trace of what SES actually reported, since the suppression record alone cannot distinguish one complaint from several.

## Final acceptance

- **Checks:** `pnpm check` green with no warnings — format, type-aware lint, typecheck, full unit suite, import smoke. The live integration suite passes against a real deployment, including the previously unexecuted claim test.
- **End state:** A hard bounce or a complaint durably suppresses the address; a suppressed address is refused before any SES call, leaving the campaign a draft with nothing submitted; a duplicate, out-of-order or unrecognised event changes nothing and never fails an invocation; SES independently refuses suppressed addresses for our configuration set. Two Lambdas share one table with per-host IAM. The ephemeral test stage is destroyed, the DKIM records removed, and no simulator address is left on the shared suppression list.
- **Deferrals or blockers:** No DLQ and no reconciliation sweep, with the reasoning and the residual cost recorded in ADR-0003: **a lost event means one wasted SES call and a campaign permanently recorded `accepted` although SES did not deliver it**. The echo is asynchronous and arrives after the campaign is finalized, and a non-draft campaign can never be resubmitted, so what the echo heals is the **address** for future campaigns — not that campaign. No un-suppress or resubscribe path — a wrongly suppressed address must be corrected out of band, acceptable while the recipient set is a configured allowlist and to be revisited with consent handling. No `DELIVERY` events and therefore no delivery history. No alarm on EventBridge `FailedInvocations`. The shared account-level suppression list stands as the accepted Open gate. The allowlist itself remains by design; replacing it is the named next slice.

## Handoff

- **Deviations (T2, T3):**
  - **Feedback history is keyed per recipient.** The plan specified `sk = FEEDBACK#<eventType>#<feedbackId>`, but one bounce event legitimately carries several `bouncedRecipients` under a single `feedbackId`. With the plan's key, recipients two and onward would collide with recipient one and be silently discarded by the conditional-is-success write. The sort key is therefore `FEEDBACK#<kind>#<feedbackId>#<lowercased recipient>`. Redelivery of the same event still writes nothing new, which was the property the plan's key existed to provide. Suppression is unaffected — it was always address-keyed and written first.
  - **`isAddressSuppressed` returns a boolean, not the record.** No consumer needs the record: T5 needs presence and T7 needs existence. Returning a boolean removes a decode path with no reader and, as a side effect, fails safe — a present-but-unreadable record reads as suppressed rather than as a corrupt-record failure. The diagnostic fields are still written to the record and are readable through `readCampaignFeedback` and the console.
  - **`readCampaignFeedback` added.** Not named in the plan, but T7 must confirm the history record and the integration suite reaches storage only through `makeStorageOperations`. Without it the history would be write-only.
  - **`functionUrl: false` is explicit on the feedback function.** The plan said "no `functionUrl`". Omitting the prop does not mean that: `FunctionCommonProps.functionUrl` defaults to `true`, which creates a **public, unauthenticated** Function URL. Caught before the live run and confirmed absent on the deployed function.
  - **Event publishing is declared in the Stack, not in `MailerLive`.** The plan put `ConfigurationSetEventDestination` in `MailerLive`. That builds at cold start too, and the default-bus ARN needs `AWS.AWSEnvironment.current`, which the deployed runtime does not provide — the first deployment returned 502 on every request with `Service not found: AWS::Environment`. `Mailer.ts` now exports `feedbackPublishing`; `alchemy.run.ts` yields it. The wiki discourages the `__ALCHEMY_RUNTIME__` guard in application code, so the declaration moved to the phase where it belongs instead.
  - **The handler reads `EMAILER_CONFIGURATION_SET` per invocation, not in the constructor.** The constructor also runs on the deploy machine, where that pinned `env` value does not exist; reading it there failed `alchemy plan` outright.
  - **The integration suite derives its one real recipient** as the first entry of `EMAILER_ALLOWED_RECIPIENTS` rather than taking a separate variable. T7 must therefore list the operator's real address first.
