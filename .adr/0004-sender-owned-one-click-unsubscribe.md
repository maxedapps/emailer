# ADR-0004: Sender-owned one-click unsubscribe

- Status: Accepted; the token decision is superseded
- Date: 2026-09-11
- Accepted: 2026-09-12

Everything else recorded here — sender-owned headers, the separate public function, the GET/POST split, address-keyed opt-out as its own item type, and the pre-send refusal — remains in effect.
- Superseded in part: [ADR-0011](0011-open-recipient-set-and-paced-dispatch.md) for the "acceptable while the recipient set is a configured allowlist" residual and for `Campaigns.send` refusing an unsubscribed address before SES. - Authority: The user asked for consent and unsubscribe handling as the slice preceding an open contact list, chose a separate unsubscribe Lambda over deriving a base URL from the request, declined both a `mailto:` entry and a `Reply-To` address on the evidence in [ADR-0002](0002-domain-sending-identity.md), deferred consent evidence and double opt-in (naming optional double opt-in as possible later work), and proposed `Alchemy.Random` for the signing key. The token construction, the GET/POST split and the storage shape are proposed here.

- Superseded in part: [ADR-0027](0027-signup-api-scoped-keys-and-double-opt-in.md) for the address-wide opt-out and "there is no resubscribe path". An opt-out now covers one list, held in the address item's `optOuts` set, and the address's own confirmed sign-up to that list lifts it.

## Context

The service can send, and it can suppress an address that bounced or complained. It offers no way for a person to stop receiving mail. Google and Yahoo both require one-click unsubscribe of bulk senders, CAN-SPAM and GDPR require honouring opt-out regardless of volume, and the feedback and suppression slice (`work/feedback-and-suppression.md`, in git history) recorded consent as the gate before the recipient allowlist may be replaced by a real contact list.

SES offers a managed path — `ListManagementOptions` with a SES-owned contact list, an inserted footer placeholder and SES-generated headers. It also permits the sender to set `List-Unsubscribe` and `List-Unsubscribe-Post` directly through the `Headers` field of `Simple` content, independently of `ListManagementOptions`. When both are present SES overrides the supplied headers, so exactly one of the two may own them.

## Decision

We own the mechanism. Every send sets `List-Unsubscribe` (one HTTPS URI) and `List-Unsubscribe-Post: List-Unsubscribe=One-Click` through the `Headers` field, plus a fixed plain-text footer carrying the same link and a configured postal address. A second Lambda with its own public Function URL serves `GET` and `POST /unsubscribe/:token`. Opt-out is stored as an address-keyed item in the existing table, and `Campaigns.send` refuses an unsubscribed address before any SES call with `recipient-unsubscribed`.

The token is `<contactId>.<hex HMAC-SHA256 of contactId>`, signed with a key minted by `Alchemy.Random` and bound into both functions' environments. It carries no address and needs no lookup table.

`GET` verifies the signature and renders a confirmation form, or answers 404; it changes nothing either way. `POST` performs the opt-out. The request body is never read, which is how both of RFC 8058's permitted encodings are accepted without parsing either.

Unsubscribe is a **separate item type from suppression**, not a sixth suppression reason. Suppression is a fact reported by a mail system; unsubscribe is a decision made by a person. Resubscribing is a legitimate future operation and un-suppressing a hard bounce mostly is not, and an operator reading a refusal must be able to tell the two apart. They share a shape and nothing else. Both are keyed by lowercased address rather than by contact. That matches what a bounce payload carries and what SES's own suppression keys on, it needs no index, and at this baseline `createContact` enforces no uniqueness on email — so contact-keyed state would leave a duplicate contact mailable. The parallel [ADR-0005](0005-contact-identity-and-membership-access-paths.md) proposes closing that last gap with an email reservation; the first two reasons stand regardless.

## Alternatives considered

**SES subscription management (`ListManagementOptions`).** Rejected: it puts the contact list in SES, making it a second store beside our table with its own notion of contacts and topics, and it would own the headers, leaving two authorities over the same unsubscribe headers ([SES subscription management](https://docs.aws.amazon.com/ses/latest/dg/sending-email-subscription-management.html)). It also constrains sends to a single recipient and requires an `{{amazonSESUnsubscribeUrl}}` placeholder in the body. We would inherit a subscription model we do not control at the moment we are about to open the recipient set.

**A route on the existing API Lambda, with the base URL derived from the request `Host`.** Genuinely simpler: no new function, no cross-resource reference, no second declaration form. Rejected because it puts an unauthenticated, publicly-reachable route inside the Bearer-guarded administrative surface, and because the links would follow whatever hostname fronted the API rather than a stable one. Note that it does **not** buy secret isolation: the API function mints the links, so it holds the signing key either way.

**A stored random token per contact instead of an HMAC.** Removes the signing key and its rotation problem entirely, and makes revocation possible. Rejected as the larger of two small designs: it needs a second item and a write on the contact-creation path to buy a revocation capability nothing asks for.

**A `mailto:` entry beside the HTTPS URI.** Rejected. RFC 8058 requires one HTTPS URI and makes `mailto:` optional, the sending domain does not receive mail, and an unsubscribe address nobody can read is an opt-out request received and not honoured — worse than not offering one.

## Consequences

- **The sent body is not byte-identical to `campaign.text`.** The footer is appended at submission. A fixed footer is deliberate: a placeholder in the campaign body would make the unsubscribe link something an author can forget.
- **`EMAILER_POSTAL_ADDRESS` is required configuration**, not optional, and an empty value fails construction. CAN-SPAM requires a valid physical postal address in commercial mail to US recipients, and the alternative to failing closed is silently sending non-compliant mail. The test stage carries a placeholder; a real address is required before real sending.
- **The signing key lives in Alchemy state and rotates when the resource or its state entry is destroyed.** `StateEncoding` writes it as a marker around plaintext — tagging, not encryption — so under `AWS.state()` the protection is the state bucket's default `AES256` encryption and its policy. A rotation invalidates every unsubscribe link in already-delivered mail, and for the ephemeral test stage that happens at every teardown. Accepted because nobody needs to know this key, which is exactly what distinguishes it from `EMAILER_API_TOKEN`: that one is a credential a person presents and must therefore be placed rather than extracted.
- **Verifying on `GET` is not acting on `GET`.** The scanner-safety rule is that a `GET` must not change state, and it does not: verification reads the signing key and no storage. What it buys is that a link whose signing key has since rotated answers 404 instead of presenting a button that cannot work — and because the key rotates whenever the stage is destroyed, such links are ordinary rather than hypothetical. The cost is that `GET` now depends on the key being present, so a missing one renders a 500 rather than a dead button, which is the better failure.
- **The public endpoint carries a concurrency cap.** A Lambda Function URL has no rate limiting of its own and cannot sit behind AWS WAF, so invocation volume is the one axis left unprotected on an endpoint that must accept unauthenticated requests. `reservedConcurrentExecutions` both caps and reserves: it bounds what a flood against this function can cost, and — the more important half — stops such a flood from consuming the account's concurrency and starving the API or the feedback consumer. It is not a substitute for a rate limiter; CloudFront with WAF in front of the URL would be, at the cost of a distribution, a certificate and DNS, and is deliberately not taken here.
- **The unsubscribe Function URL is genuinely public.** `authType: "NONE"` upserts a public `lambda:InvokeFunctionUrl` permission, so the token is the only authorization and is verified in the handler. The blast radius of a forged token is one address opted out — the conservative direction. Forging a signature is infeasible without the key, so the only response distinction an attacker can reach is between a rejected token and an accepted one, which tells them nothing they did not already supply.
- **A page that claims success must mean it.** Mail providers treat a 2xx from the one-click POST as the opt-out being honoured and do not retry. Any path that renders the confirmation without a durable write — a storage failure, a timeout, a contact that cannot be resolved — would convert a transient fault into a permanent one on the single interaction the recipient gets. Those paths return non-2xx and claim nothing. This costs no machinery: an uncaught storage failure already becomes a logged 500, so the requirement is that the handler not suppress it for the sake of a uniform page. A repeat request is the one case that is genuinely 200 without a write, because the conditional write makes it a real no-op.
- **There is no resubscribe path.** An address opted out by mistake must be corrected out of band. Acceptable while the recipient set is a configured allowlist; it must be revisited with the open contact list. Revisited in [ADR-0006](0006-consent-survives-a-contacts-address-change.md), which keeps address keying and refuses to move a contact off an opted-out address, since the open contact list had made that change a way around this rule.
- **DKIM coverage of the two headers is proven.** Confirmed on 2026-09-14 against a delivered message whose `Authentication-Results` showed `dkim=pass header.d=mail.example.com`: the verifying signature carried `h=From:To:Subject:MIME-Version:Content-Type:Content-Transfer-Encoding:List-Unsubscribe:List-Unsubscribe-Post:Message-ID:Date`. See [ADR-0009](0009-account-level-sending-identity.md). SES signs headers supplied through `Simple` content `Headers`, the `Content.Raw` fallback below was not needed and has not been built. The original reasoning is kept because it is what made the check a gate rather than an afterthought:
- **(Superseded by the line above.) DKIM coverage of the two headers was inferred, not proven.** RFC 8058 requires both fields in the `h=` tag of a valid signature, and AWS documents nowhere which headers SES signs. Captured SES mail shows the signer enumerating the headers actually present, including both unsubscribe fields under a sender's own Easy DKIM `d=`, but those captures are raw/SMTP sends. The deployment check reads `h=` from a delivered message; if it lacks them, the fallback is `Content.Raw` MIME inside `makeSubmit`. That is confined to one function, but it is not a small change: hand-composed MIME, RFC 2047 encoded-words for non-ASCII subjects, a body transfer encoding, and every assertion in that function's test describe reshaped.
- **The cross-function reference forces a different declaration form.** `Api.ts` must embed a link pointing at the unsubscribe function's URL, and Alchemy's inline `Function` class form always builds when yielded — yielding it inside `apiProps` would run the unsubscribe function's props and init inside the API Lambda at every cold start, resolve its configuration against the wrong environment, and pull its handler into the API's bundle. The unsubscribe function is therefore declared as a bare tag in a module that imports no handler, with its `.make` Layer provided to the Stack program. Three functions, two declaration forms: the asymmetry is a consequence of the reference, not a style choice.
- **The token is longer than a default path parameter.** At 36 characters of contact id, a separator and a 64-character hex digest it is 101 characters, and Effect's router caps a path parameter at 100 by default — a capped route answers every real link with a 404. The route declares the length it carries rather than shortening the signature to fit a default, because the cap is an arbitrary default and the digest width is not.
- **`Campaigns.send` asks one address question instead of two.** `addressStatus` replaces `isAddressSuppressed` and answers `"mailable" | "unsubscribed" | "suppressed"` in one operation, at the cost of a second `GetItem` on the send path whenever the address is not opted out. It reads the unsubscribe key first and returns on a hit, so precedence is a property of the operation rather than of the caller, and it is pinned by test rather than left to the order the checks happened to be written in.

## Confirmation

`Unsubscribe.test.ts` covers the token round trip and each way a token can be rejected, with the secret supplied through the same `Config` read the deployed function uses. `UnsubscribePage.test.ts` drives the composed router and covers the property that matters most — a `GET` writes nothing even for a token it accepts, so a scanner or link prefetcher cannot opt anyone out — plus a forged signature refused on `GET` as well as `POST`, plus idempotent repeat `POST`s and a rejected signature. `Storage.test.ts` pins the precedence of `"unsubscribed"` over `"suppressed"` and that a failed read never reports `"mailable"`. `Mailer.test.ts` asserts both headers and the footer on the built request. Live confirmation is recorded in the slice plan (`work/consent-and-unsubscribe.md`, in git history) under T9, including the delivered message's `h=` tag.
