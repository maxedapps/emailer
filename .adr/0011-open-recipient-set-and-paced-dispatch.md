# ADR-0011: Open recipient set with a paced, resumable dispatcher

- Status: Accepted
- Date: 2026-09-15
- Confirmed: 2026-09-15. Live gate on ephemeral stage `test-b` passed; the stage was destroyed.

## Context

A campaign today is refused unless its list has exactly one member whose address is in a configured allowlist, and the send runs synchronously inside a 60-second API request with one SES submission. That was the first slice's safety rail. Suppression, consent and one-click unsubscribe now exist, so the rail has done its job.

Mass sending needs four things the current design lacks: an audience read that pages, per-recipient outcomes and progress, work that outlives one Lambda invocation, and a send rate that respects the account's SES quota across every runner. SES quotas are per account and Region and shared with another workload in this account; a per-second overrun is throttled, and a throttle is currently classified as a definitive rejection that ends the campaign permanently.

Effect 4 ships `RateLimiter` under `effect/unstable/persistence` with a pluggable `RateLimiterStore`. Its fixed-window algorithm in delay mode is a queue-style scheduler: every consumer takes a slot and is told how long to wait until its slot opens, and the store is the single point of coordination. The installed stores are process-local memory and Redis. The store interface has two methods that matter and two adaptive ones this project does not use.

## Decision

- **No allowlist.** `EMAILER_ALLOWED_RECIPIENTS`, the `allowedRecipients` service field and the `recipient-not-allowed` refusal are deleted. The recipient-safety rail becomes a testing convention with one test-side guard: automated and manual tests send only to SES mailbox simulator addresses, labelled per run, the integration support refuses to send a list containing any other address, and the operator mailbox is used sparingly for header checks. Real recipients wait until this decision and ADR-0010 are both implemented.
- **Asynchronous send.** `POST /campaigns/:id/send` moves the campaign from `draft` to `queued`, mints a run token, and sends one wake-up message to a standard SQS queue. The API never submits to SES again and no longer constructs the mailer, so its role loses `ses:SendEmail`. `send` on an already queued campaign re-sends the wake-up, which closes the write-then-enqueue gap; a failed enqueue after the `queued` write is reported as a storage failure so the caller retries.
- **A dispatcher Lambda processes exactly one page of members per invocation.** It consumes the queue one message at a time, begins the run (reading the campaign record), pages fifty members from the persisted cursor, skips unsubscribed and suppressed addresses, claims a per-recipient row, submits under the rate limiter, settles the row and the campaign counters in one transaction, checkpoints the cursor conditionally, and then either completes, pauses, or enqueues the same wake-up as its continuation. A continuation is enqueued only after a won checkpoint, so a duplicate delivery cannot start a second chain, and every two-page campaign exercises the continuation.
- **Per-recipient rows are the unit of work.** `SEND#<contactId>` is created with an absence condition and settled as `accepted`, `rejected`, `uncertain` or `skipped`. It no longer copies the campaign's subject and text. A row is never re-attempted: an uncertain submission stays uncertain, exactly as today.
- **Campaign states** are `draft`, `queued`, `sending`, `paused`, `completed`, with counters `accepted`, `rejected`, `uncertain`, `skipped`, an internal cursor and a run token. Run-level transitions and claims are conditional on state and run token, so a stale runner after a resume cannot claim or checkpoint; settling a row it already claimed is deliberately allowed.
- **Pacing through `RateLimiter`** in fixed-window delay mode, one key per stage table, backed by a DynamoDB `RateLimiterStore` in that table. The limit is `max(1, floor(MaxSendRate × 0.8))`, read from `GetAccount` at the start of every slice. The 20 percent margin covers the other workload on the account, whose sends the limiter cannot see. The dispatcher asks the limiter for its delay, checks that the delay plus one submission fits its remaining budget, and only then sleeps and sends. The store implements `fixedWindow` with the algorithm of Effect's memory and Redis stores: one conditional `UpdateItem` in the common path and a reset conditioned on the item having expired; `tokenBucket` and the adaptive methods fail as unsupported.
- **Throttle backs off, then pauses.** A `rate-limited` submission provably never sent; the dispatcher retries the same recipient after 1, 2 and 4 seconds. If all fail, that recipient is settled `rejected` and the campaign pauses with reason `rate-limited`, so a co-tenant's burst never silently rejects an audience.
- **Daily quota pauses, it does not refuse.** At every slice start the dispatcher compares `SentLast24Hours` with `min(Max24HourSend × 0.9, EMAILER_DAILY_SEND_CEILING)`; if the budget is spent the campaign pauses with reason `daily-quota`. A `sending-paused` rejection from SES pauses with reason `sending-paused`. `POST /campaigns/:id/resume` mints a new run token and re-enqueues; on any other state it returns the campaign unchanged, as `send` does. The optional ceiling is the volume ramp for a new domain.
- **Membership is read live, not snapshotted.** A member added behind the cursor is mailed, one added ahead of it is not, and there is no list-version check. `MembershipConflict` is deleted.

## Alternatives considered

1. **Keep the allowlist as a per-recipient skip during a first step.** Safer to build behind, but it leaves a rail the user has decided against and a second step to remove it. Rejected by the user.
2. **FIFO queue with one message group per campaign.** Guarantees one runner per campaign at the queue level. Unnecessary once the shared limiter handles the rate and the checkpoint is conditional: two runners on one campaign cannot double-send and the loser stops at its first failed checkpoint. Rejected as a second mechanism for a solved problem.
3. **Process-local `RateLimiter` store with one runner.** Exact only while exactly one runner exists, which a standard queue cannot guarantee and overlapping campaigns contradict. The user wants a shared store from the start.
4. **Redis-backed store.** Shipped by Effect, but adds a Redis service to a serverless stack for one counter.
5. **One queue message per recipient.** Per-recipient retry and dead-lettering for free, but a second stage to expand the audience, and the per-recipient row already provides idempotency and audit. More moving parts for no new guarantee.
6. **Looping pages in-process until near the time budget.** Fewer SQS hops, but the continuation path would then run only for campaigns longer than one invocation, which means first in production. One page per invocation costs a sub-second hop per fifty recipients and proves the continuation on every run.
7. **Step Functions distributed map.** The canonical AWS answer to paced fan-out, but a new ASL surface with no project knowledge and harder local tests.
8. **Self-invoking Lambda without a queue.** Fewer resources, but a Lambda invoking itself is the construction-time self-reference Alchemy makes awkward, and the queue gives continuation, retries and dead-lettering for free.
9. **Reconciling rows claimed by a crashed slice.** One more branch on redelivery would settle them `uncertain`. Rejected for now: the exposure is one page, the rows show it, and the residual is recorded below.

## Consequences

- **At-least-once delivery shapes every write.** The wake-up message may be delivered twice; every run-level write is conditional on state, run token and cursor, and a redelivered page claims nothing twice. Skipped recipients get a row too, so skip counts are exact. Runners are at least one per active campaign, usually exactly one.
- **The limiter's delay grows with concurrent runners.** Each runner waits about `runners / limit` seconds per send. No concurrency cap is set; if that ever changes, the dispatcher's reserved concurrency is the knob.
- **The limiter coordinates one stage.** The table is per stage, so two stages sending at volume in the same account each pace at their own 80 percent. Only one stage may send at volume per account; a second sender needs a shared table or a shared external store.
- **A failed invocation delays the campaign by the visibility timeout** (30 minutes) before SQS redelivers. A deterministic failure dead-letters the wake-up after five receives and leaves the campaign `sending`; `resume` does not apply, and the recovery is an SQS redrive of that message, recorded in the README.
- **Rows claimed by a crashed slice stay `unconfirmed`** and are never settled or counted, so the counters can sum to fewer than the members. The rows are the record; the exposure is at most one page.
- **The store and `GetAccount` add one call per send and one per slice.** At tens of sends per second that is negligible on an on-demand table.
- **Conditional writes are single-attempt.** The AWS client retries transient answers by default, and a retried conditional write that had already applied returns a condition failure, which the dispatcher would read as a lost race: a checkpoint acknowledged without a continuation, a claim never mailed. `updateIf` and `runTransaction` therefore opt out of client retries, as the mailer does; a transient answer is `unavailable`, the invocation dies and SQS redelivers, and the API answers 503 for the caller to retry.
- **`RateLimiter` is an `unstable` module.** Its API may change before Effect 4.0 final; the store adapter is the only place that would need to follow.
- **Table write surface**: `UpdateItem` joins `CampaignStore`, and a new capability owns the limiter's `UpdateItem`. The API's IAM narrows (no `ses:SendEmail`); the dispatcher's is the API's former send surface plus `sqs:SendMessage`, `ses:GetAccount` and the queue consumer grants. ADR-0008 records the change through its lifecycle header; its body keeps the earlier table as accepted rationale.
- **A recipient that triggers a pause is recorded `rejected`** and not re-attempted after resume. One recipient per pause is the accepted cost of never re-submitting a claimed row.
- **The API loses four error shapes** (`InvalidAudience`, `MembershipConflict`, `SendUnconfirmed`, `SendStatusUnrecorded`). `send` exits the CLI with success as soon as the campaign is queued; progress is polled.
- **The account suppression list may gain simulator entries** per test run under labelled addresses; teardown inspection stays as documented.
- **Transient-bounce escalation and feedback counts in `campaigns get`** are not part of this decision. The user moved both to the reputation lane on 2026-09-15 and postponed that lane until lanes A and B have landed.

## Confirmation

Confirmed on 2026-09-15 against ephemeral stage `test-b`, then destroyed. Account `SendQuota` before the run: `MaxSendRate=26`, `Max24HourSend=50000`, `SentLast24Hours=19`; paced limit `floor(26 × 0.8) = 20`. A campaign to sixty labelled `success+` simulator addresses completed with `progress.accepted === 60`, sixty accepted `SEND#` rows, the `RATELIMIT#ses-send` item written, and nineteen `finishedAt`-second buckets none of which exceeded 20. Two concurrent `send` calls both returned HTTP success; one response was already `sending` because the API re-reads after enqueue and the dispatcher is fast — one row per member still held. An empty list completed with counters 0. The test-side simulator guard refused `@example.invalid`. A second campaign to previously bounced and complained addresses completed with `skipped: 2`; a second campaign after opt-out completed with `skipped: 1`. `DispatchFailures` had `ApproximateNumberOfMessages=0`. No labelled simulator entries remained on the account suppression list. Per-second SES throttle error names were not observed (no `rate-limited` pause); the mailer already maps `TooManyRequestsException`, `ThrottlingException` and `LimitExceededException` to `rate-limited`. Destroy reported 21 succeeded; no `emailer-test-b` functions, no `Emailer-*-test-b` queues, and `alchemy state list Emailer` showed no `test-b`.
