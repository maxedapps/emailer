# Amazon S3: objects, versions and reliable references

[AWS](aws.md) · [DynamoDB](dynamodb.md) · [IAM and secrets](iam-and-secrets.md) · [CloudFront and private origins](cloudfront.md)

Amazon S3 stores objects identified by a bucket and key. A key is a name, not a directory path with filesystem semantics; prefixes organize names and support listing or access-policy scope. An object carries a body and metadata, and a version-enabled bucket can retain multiple versions under the same key. Large documents, imports, exports and immutable artifacts fit this model better than embedding them in queue messages or database items. [S3 overview](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html)

## Choose an object identity

Use a stable key for a replaceable current value, or a unique/versioned key when older readers must continue to see the original bytes. A database reference can include bucket, key, version ID, content type, size and checksum according to the consumer's needs. Do not assume a filename or user-supplied path establishes ownership; generate or validate the authorized prefix before granting access.

S3's strong read-after-write consistency applies to supported object operations after a successful write. It does not combine an object write and a DynamoDB update into one transaction. A common sequence is upload → verify success → commit the durable reference. If the final reference commit fails, an unreferenced object remains; cleanup can remove it after a grace period. Reversing the sequence can leave an acknowledged record pointing at an object that was never uploaded. [Consistency model](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html)

## Prevent accidental overwrites

A plain write to an existing key can replace its current contents. Use a conditional write when the operation requires stronger concurrency semantics: `If-None-Match: *` creates only when no current object exists, while `If-Match` compares the current ETag before replacing it. Treat a failed precondition as a concurrency outcome and re-read before deciding whether to retry; do not turn it into an unconditional overwrite. Versioning retains history but does not make a lost-update race harmless. [Conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)

An ETag is useful for the conditional request contract. Do not universally treat it as the MD5 of the full object: upload mode and encryption can affect its meaning. Use an explicitly supported checksum when integrity verification requires a particular algorithm, and retain that checksum with the reference when later consumers need to validate the bytes. [Object integrity](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity.html)

## Versioning, deletion and lifecycle

Enabling versioning causes subsequent writes to create object versions. An ordinary delete generally creates a current delete marker rather than erasing all older versions; a version-specific delete can permanently remove a selected version. A reference to an explicit version is therefore different from a reference to the current object at a key. Suspending versioning is not the same as returning the bucket to its original never-versioned state. [Versioning](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Versioning.html)

Lifecycle rules for current objects and noncurrent versions have different effects. Expiring the current view may leave historical storage behind. Decide separately how long to preserve old artifacts, delete markers and incomplete multipart uploads. For deployment state, restoration also requires reconciling the restored metadata with the actual cloud; recovering an old object does not roll back other services.

## Presigned access

A presigned URL delegates a particular operation using the signing principal's credentials. Possession of the URL is sufficient to exercise that delegated access while it remains valid, so treat it as a bearer credential. It is not inherently single-use. Temporary credentials can expire before the requested URL lifetime, and the URL cannot grant permissions the signer does not have. [Presigned URLs](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)

Authorize the bucket, key and operation before signing. Keep expiry short enough for the intended transfer and prevent an upload from selecting another owner's key. A signed upload to an existing key can overwrite its current object unless the operation includes suitable preconditions. Avoid logging full URLs, and preserve signed headers exactly when making the request. Network, checksum and policy errors require different remedies; regenerating a URL does not repair an invalid destination policy.

## Events and asynchronous processing

S3 notifications can route object events to supported SNS, SQS, Lambda or EventBridge destinations. They are at-least-once notifications, so consumers must tolerate duplicates and delays. Direct notification destinations do not include SQS FIFO; EventBridge is an alternative route when FIFO delivery is needed. Writing processed output into the same triggering prefix can create a feedback loop. [S3 event notifications](https://docs.aws.amazon.com/AmazonS3/latest/userguide/EventNotifications.html)

Correlate events to the intended object version and make processing repeatable. A notification is not a transaction with a separate database reference; depending on upload flow, the object event can arrive before the application commits its metadata. Handle missing reference records deliberately rather than deleting valid data immediately.

## Investigation and source lookup

For access failures, inspect the signing or runtime principal, object versus bucket ARN scope, bucket policy, explicit denies and KMS key permissions. For missing objects, compare current-key lookup with version-specific lookup and delete markers. For repeated processing, inspect notification filters, output prefixes and consumer idempotency.
